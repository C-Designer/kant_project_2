PR 에서 배포까지: 코드가 운영에 닿는 길

브랜치에서 고친 코드가 운영 주소에 뜨기까지 어떤 관문을 지나고, 각 관문은 누가 지킵니까?

이 저장소의 CI/CD 는 두 시스템이 나눠 맡습니다. GitHub 은 main 에 무엇이 들어갈지를 지킵니다. PR 마다 GitHub Actions 가 검사 네 개를 돌리고(CI), 룰셋이 네 검사를 모두 통과한 PR 로만 main 을 바꿀 수 있게 합니다. Vercel 은 main 에 들어온 것을 운영에 올립니다(CD). .github/workflows/ci.yml 에는 배포 단계가 없고, Vercel 의 Git 연동이 main 의 새 커밋을 보고 프로젝트 두 개를 각각 빌드합니다.

1 · PR<github-id>/<type>-<설명> 브랜치를 push 하고 main 으로 PR 을 엽니다.
2 · CI 4개 jobbranch-name, backend-lint, backend-test, frontend 가 동시에 돕니다.
3 · 룰셋네 체크가 모두 통과해야 병합할 수 있습니다. 예외 목록이 비어 있어 소유자도 예외가 아닙니다(룰셋을 끄는 권한은 소유자에게 남습니다).
4 · main 병합화면(Next.js)과 API(FastAPI) 두 Vercel 프로젝트가 각자 빌드합니다.
5 · 주소 전환빌드가 성공하면 운영 주소가 새 배포를 가리키고, 실패하면 이전 배포가 계속 응답합니다. 요청을 보내 확인하는 단계는 없습니다.

2단계와 3단계는 이름으로 이어집니다. 룰셋이 요구하는 체크 이름은 CI job 의 name: 값과 글자까지 같습니다.

{ "type": "required_status_checks", "parameters": { "strict_required_status_checks_policy": false, "required_status_checks": [ { "context": "branch-name" }, { "context": "backend-lint" }, { "context": "backend-test" }, { "context": "frontend" } ] } }
  1. 필수 상태 체크 규칙입니다. 나열한 체크가 모두 성공으로 보고돼야 PR 을 병합할 수 있습니다(GitHub 문서, 2026-10-15 확인).
  2. false 라서 PR 브랜치가 최신 main 을 따라잡지 않아도 병합할 수 있습니다. 이 선택의 대가는 "원리: 필수 체크" 섹션에서 봅니다.
  3. context 이름은 ci.yml 의 job name:(18·36·48·66줄)과 같습니다. 각 항목에 integration_id 가 없어 체크는 이름으로만 맞춰지므로, 쓰기 권한이 있는 사람이나 앱이 같은 이름으로 보고한 상태도 통과로 인정됩니다(GitHub 룰셋 문서, REST 문서, 2026-10-15 확인). 출처를 GitHub Actions 로 묶으려면 이 저장소의 check run 이 보고하는 앱 id 15368 을 integration_id 로 적습니다. 다만 pull_request 실행은 PR 쪽 ci.yml 을 그대로 쓰고 승인 수가 0 이므로, 쓰기 권한자가 PR 에서 job 내용을 바꾸는 것까지 막지는 못합니다.
  4. 처음(PR #1, 2026-10-12)에는 체크가 세 개였습니다. PR #26(2026-10-14)이 backend-test job 을 만들면서 이 줄도 함께 더했습니다.

병합 뒤에는 화면 프로젝트(kant-lovecode)와 API 프로젝트(kant-lovecode-api)가 따로 빌드되고 따로 배포됩니다. 그래서 화면은 새 버전인데 API 는 아직 옛 버전인 순간이 생길 수 있고, README 는 화면·API 계약을 바꿀 때 전후 버전이 서로 호환되게 하라고 적습니다. PR #30 병합 때 화면은 02:08:18Z, API 는 02:09:45Z 에 Production 도메인으로 바뀌어 약 87초 동안 화면만 새 배포였습니다. Hobby 플랜은 배포를 한 번에 하나씩 빌드하므로(Vercel 빌드 관리 문서, 2026-10-15 확인), API 빌드는 화면 빌드가 끝난 직후에야 시작했습니다. 이번 PR 은 백엔드를 바꾸지 않아 문제가 없었지만, 계약을 바꾸는 PR 이라면 그동안 새 화면이 옛 API 를 부릅니다. 빌드가 실패하면 기존 배포가 유지된다고 README 가 적고 있으며, Vercel 빌드 문서도 빌드가 성공한 뒤에 Production 도메인을 갱신한다고 설명합니다(2026-10-15 확인).

빌드 성공은 요청을 처리해 봤다는 뜻이 아닙니다. API 의 BERT 모델은 첫 ready() 호출 때 올라갑니다(backend/lovecode/service.py:41). 가중치 해시는 빌드가 이미 확인하지만(build_model.py 43줄), 환경변수 값이 빠지거나 틀린 것, 모델이 실제로 올라가는지는 빌드가 보지 않습니다. 이런 문제는 운영 주소가 옮겨진 뒤 첫 요청에서 드러납니다. ready() 가 False 이면 health 는 200 응답에 analysis_ready: false 를 담고, 분석 요청은 503 ANALYSIS_UNAVAILABLE 을 받습니다(backend/lovecode/api.py:155). 이때 복구 수단은 Vercel 의 Instant Rollback 입니다. Hobby 는 바로 이전 배포로만 되돌릴 수 있습니다. 되돌리면 운영 도메인 자동 연결이 꺼지므로, Undo Rollback 이나 vercel promote 로 배포를 다시 승격하기 전까지는 main 에 병합해도 운영에 반영되지 않습니다. 되돌린 배포는 프로젝트 설정의 현재 값이 아니라 그 배포를 만들 때의 환경변수를 씁니다(Vercel Instant Rollback 문서, 2026-10-15 확인).

지금 읽는 이 페이지도 같은 길로 나갑니다. build.py 가 frontend/public/learn/index.html 을 함께 쓰므로, 학습 페이지를 고친 PR 도 CI 를 통과해 main 에 병합되고 화면 프로젝트가 다시 배포돼야 /learn 에 보입니다. 걸리는 시간은 짧습니다. 2026-10-15 PR #30 의 실행에서 네 job 은 동시에 시작했고, 가장 오래 걸린 frontend 와 backend-test 가 약 24초였습니다.

ci.yml: 네 job 을 한 줄씩

CI 는 언제 돌고, 같은 PR 에 push 가 겹치면 어떻게 되며, 네 job 은 각각 무엇을 설치하고 무엇을 검사합니까?

워크플로 파일 하나에 job 네 개가 있습니다. 서로 needs: 로 묶이지 않아 동시에 시작하고, 모두 ubuntu-latest 러너에서 돕니다. 먼저 파일 머리의 실행 조건과 공통 설정을 봅니다.

name: CI on: pull_request: branches: [main] push: branches: [main] concurrency: group: ci-${{ github.ref }} cancel-in-progress: true permissions: contents: read
  1. main 을 향한 PR 이 열리거나 그 PR 에 커밋이 push 될 때 돕니다.
  2. main 에 push 될 때도 돕니다. 룰셋이 main 직접 push 를 막으므로 실제로는 PR 병합 직후의 실행입니다. 예약 실행이나 수동 실행(workflow_dispatch)은 없습니다.
  3. 같은 group 이름을 가진 실행끼리 묶습니다. github.ref 는 PR 실행에서 refs/pull/번호/merge, main push 에서 refs/heads/main 입니다(GitHub 이벤트 문서). 그래서 PR 마다 group 이 하나씩 생깁니다.
  4. 같은 group 에서 진행 중인 실행이 있으면 새 실행이 그것을 취소합니다(GitHub 동시성 문서). PR 에 커밋을 연달아 push 하면 마지막 커밋의 실행만 끝까지 갑니다.
  5. 워크플로가 받는 GITHUB_TOKEN 에 저장소 읽기 권한만 줍니다. 어느 job 도 저장소에 쓰거나 배포하지 않으므로 이것으로 충분합니다.

첫 job 은 코드를 받지도 않고 브랜치 이름만 봅니다.

branch-name: name: branch-name runs-on: ubuntu-latest steps: - name: Check /- if: github.event_name == 'pull_request' env: HEAD_REF: ${{ github.head_ref }} AUTHOR: ${{ github.event.pull_request.user.login }} run: | owner="$(printf '%s' "$AUTHOR" | tr '[:upper:]' '[:lower:]')" pattern="^${owner}/(feat|fix|docs|refactor|test|chore)-[a-z0-9][a-z0-9-]*$" if [[ !   1. 이 name 이 룰셋의 체크 이름(context)이 됩니다.
  2. PR 실행에서만 검사합니다. main push 에는 PR 작성자도 head 브랜치도 없으므로 이 단계를 건너뛰고 job 은 통과로 끝납니다.
  3. 브랜치 이름과 작성자 아이디를 env 로 넘깁니다. run: 안에 ${{ }} 로 바로 넣지 않는 이유는 원리 섹션에서 봅니다.
  4. GitHub 아이디에는 대문자가 들어갈 수 있으므로(C-Designer) 소문자로 바꿔 비교합니다.
  5. <아이디>/<6종류 중 하나>-<소문자·숫자로 시작하는 설명> 정규식입니다. 다른 사람의 아이디로 시작하는 브랜치도 여기서 걸립니다.
  6. bash 의 [[ … =~ … ]] 는 오른쪽을 따옴표 없이 쓰면 정규식으로 해석합니다.
  7. ::error:: 는 워크플로 명령으로, 로그에 오류를 찍고 주석(annotation)을 만듭니다(GitHub 문서). 이름을 고치려면 새 이름으로 다시 push 하고 PR 을 새로 엽니다.
  8. 종료 코드 1 이 job 을 실패로 만들고, 필수 체크가 실패했으므로 병합이 막힙니다.

두 백엔드 job 은 같은 방식으로 Python 을 준비하지만 설치하는 범위가 다릅니다. lint 는 ruff 만 있으면 됩니다.

backend-lint: name: backend-lint runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: astral-sh/setup-uv@v6 with: python-version: "3.12" # dev 그룹만 설치해 torch 등 무거운 런타임 의존성을 받지 않는다. - run: uv sync --frozen --only-group dev - run: uv run --no-sync ruff check backend tests scripts
  1. 저장소 코드를 러너에 받습니다.
  2. uv 를 설치하고 Python 3.12 를 준비합니다. 루트 pyproject.toml 의 requires-python(>=3.12,<3.13)과 맞습니다.
  3. --only-group dev 는 프로젝트 의존성(torch, transformers, langchain 등)을 빼고 dev 그룹(pytest, pytest-asyncio, ruff, korean-lunar-calendar)만 설치합니다. --frozen 은 uv.lock 을 고치지 않고 그대로 씁니다.
  4. uv run 은 기본적으로 명령 전에 프로젝트 환경을 갱신합니다. --no-sync 가 없으면 이 단계에서 프로젝트 의존성 전체를 설치하려 들기 때문에 끕니다.

테스트 job 은 pytest 에 필요한 것을 설치하되, 가장 무거운 torch 와 CUDA 패키지만 뺍니다.

backend-test: name: backend-test runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: astral-sh/setup-uv@v6 with: python-version: "3.12" # 테스트는 torch를 import하지 않는다(BERT 코드는 함수 안에서만 import). # torch·triton·CUDA 패키지(수 GB)만 빼고 uv.lock 그대로 설치한다. - name: Install without torch/CUDA run: | exclude=$(grep -oP '^name = "\K(torch|triton|nvidia-[^"]+|cuda-[^"]+)(?=")' uv.lock \ | sort -u | sed 's/^/--no-install-package /') uv sync --frozen $exclude # tests/conftest.py가 실제 HTTP를 막으므로 유료 API 호출은 없다. - run: uv run --no-sync pytest -q
  1. 이 job 이 성립하는 전제입니다. backend/lovecode/bert.py 는 import torch 를 함수 본문 안에만 두므로(16·35·48·60·93줄) 모듈을 import 하는 것만으로는 torch 가 필요 없습니다.
  2. uv.lock 의 name = "…" 줄에서 torch, triton, nvidia-*, cuda-* 이름만 뽑습니다. -P 는 PCRE 문법이고, \K 는 그 앞부분을 결과에서 빼며, (?=") 는 닫는 따옴표를 확인만 하고 결과에 넣지 않습니다.
  3. 중복을 없애고 이름마다 앞에 --no-install-package 를 붙입니다. 지금 uv.lock 에서는 20개(torch, triton, cuda-* 3개, nvidia-*-cu12 15개)가 나옵니다.
  4. $exclude 를 따옴표 없이 써서 셸이 공백마다 나눠 여러 인자로 넘깁니다. 이 20개만 빼고 나머지(transformers 포함)는 uv.lock 그대로, dev 그룹과 함께 설치됩니다.
  5. 네트워크와 유료 API 가 필요 없는 이유는 tests/conftest.py 의 autouse 픽스처입니다. 원리 섹션에서 봅니다.

제외 목록을 손으로 적지 않고 uv.lock 에서 뽑으므로, torch 버전을 올려 딸려 오는 nvidia 패키지 이름이 바뀌어도 워크플로를 고칠 필요가 없습니다. 마지막 job 은 프런트엔드입니다.

CI 가 하지 않는 일도 있습니다. scripts/verify.py 는 위 검사 여섯 가지에 데이터셋 검증과 학습 dry-run 을 더한 여덟 명령을 돌립니다. 뒤의 둘은 CI 에 없고, CONTRIBUTING.md 가 PR 전에 로컬에서 실행하도록 안내합니다. 또 어떤 테스트도 BertModel 을 만들거나 bert.py 의 함수를 부르지 않습니다(그래서 torch 를 빼도 통과합니다). 운영 설정(LC_CLASSIFIER_MODE=local)이 쓰는 BERT 추론 경로는 CI 에서 한 번도 실행되지 않고, 로컬에서 torch 를 설치한 채 pytest 를 돌려도 마찬가지입니다.

CI 설정의 각 줄은 어떤 실패를 막고, 무엇은 막지 못합니까?

룰셋의 앞부분은 main 으로 들어가는 길을 PR 하나로 좁힙니다.

{ "name": "main-protection", "target": "branch", "enforcement": "active", "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } }, "bypass_actors": [], "rules": [ { "type": "deletion" }, { "type": "non_fast_forward" }, { "type": "pull_request", "parameters": { "required_approving_review_count": 0, "dismiss_stale_reviews_on_push": false, "require_code_owner_review": false, "require_last_push_approval": false, "required_review_thread_resolution": false } },
  1. 규칙이 실제로 적용되는 상태입니다.
  2. ~DEFAULT_BRANCH 는 저장소 기본 브랜치, 곧 main 을 가리킵니다.
  3. 예외 목록이 비어 있어 저장소 소유자도 같은 규칙을 따릅니다.
  4. main 삭제를 막습니다.
  5. force push 를 막습니다. 이미 main 에 들어간 이력을 덮어쓸 수 없습니다.
  6. main 의 모든 변경이 PR 을 거쳐야 합니다.
  7. 승인 수는 0 입니다. GitHub 은 0~10 을 허용합니다(GitHub 룰셋 문서). 리뷰는 CONTRIBUTING.md 에 권장 사항으로만 남겨 두었습니다.

PR 전용과 필수 체크를 함께 쓰는 이유. 길을 PR 하나로 좁히고 그 길에 CI 를 세우면 "main 에 들어온 변경은 하나하나 네 검사를 통과한 변경" 이 됩니다(합쳐진 결과까지 검사됐는지는 아래 strict 에서 봅니다). Vercel 의 Git 연동은 main 커밋에서만 배포를 만들므로, 이 길로 운영에 올라가는 코드는 같은 조건을 거칩니다. 다만 git.deploymentEnabled 는 커밋이 일으키는 자동 배포만 정합니다(Vercel Git 설정 문서). Vercel 은 로컬에서 vercel --prod 를 실행해도 Production 배포가 만들어진다고 설명하므로(Vercel 환경변수 문서, 2026-10-15 확인), 이 명령은 PR·CI·룰셋을 거치지 않은 로컬 파일을 그대로 운영에 올립니다. 이 길은 저장소 설정으로 막을 수 없습니다. Vercel 은 CLI 로 Production 에 배포하는 권한(Full Production Deployment)을 따로 두고 Developer 역할에서 뺄 수 있게 하지만, 이런 역할은 Pro·Enterprise 플랜에만 있습니다(Vercel 역할 문서, 2026-10-15 확인). Hobby 플랜인 지금은 운영 배포를 main 병합으로만 한다는 약속에 기댑니다.

룰셋 JSON 은 저장소에 있어도 저절로 적용되지 않습니다. 저장소 소유자가 gh api 로 올려야 합니다. 이 저장소는 개인 계정 소유라 GitHub 이 권한을 소유자와 협업자 두 단계로만 나눕니다(GitHub 문서, 2026-10-15 확인). 협업자는 push 와 PR 병합을 할 수 있지만 admin 권한이 없어 룰셋을 바꾸거나 끌 수 없고, 그 권한은 소유자 한 명에게 남습니다. CONTRIBUTING.md 가 말하는 Write 와 Admin 의 구분은 저장소를 조직으로 옮겨 역할을 고를 수 있게 되었을 때 생깁니다. 체크 이름과 job 이름이 같아야 하므로, job 을 추가하거나 이름을 바꾸면 룰셋도 함께 고쳐야 합니다. PR #26 이 backend-test 를 만들 때 그렇게 했습니다.

strict 를 끈 대가. pull_request 실행은 PR 브랜치 그대로가 아니라 GitHub 이 만든 병합 커밋(refs/pull/번호/merge)을 검사합니다. 이 병합 커밋은 CI 가 돈 시점의 main 을 기준으로 합니다. strict 를 켜면 브랜치가 base 브랜치와 최신이어야 병합할 수 있지만(GitHub 룰셋 문서), 꺼 둔 지금은 PR A 와 PR B 가 각자 옛 main 위에서 통과한 뒤 연달아 병합될 수 있습니다. 둘을 합친 코드는 병합 뒤의 main push 실행에서 처음 검사되고, 저장소의 설정 파일(ci.yml, 두 vercel.json)에는 Vercel 배포가 그 결과를 기다리게 하는 장치가 없습니다. PR 마다 main 을 다시 받아 CI 를 돌리는 수고가 없는 대신 생기는 틈입니다.

배포가 main 검사를 기다리게 하려면. 이 틈은 실제로 열려 있습니다. PR #30 은 2026-10-15 02:08:01Z 에 병합됐고, Vercel API 의 배포 기록(aliasAssignedAt)을 보면 화면 프로젝트의 새 배포가 02:08:18Z 에 Production 도메인에 연결됐습니다. 같은 커밋의 main 실행에서 backend-test·frontend 는 02:08:29Z·02:08:32Z 에 끝났으므로, 운영이 main 검사보다 먼저 바뀐 것입니다. Vercel 의 Deployment Checks 를 켜면 Production 배포는 만들어지지만, 지정한 GitHub 체크가 모두 통과할 때까지 도메인에 연결되지 않습니다(Vercel Deployment Checks 문서, 2026-10-15 확인). 체크는 프로젝트 설정에서 고르므로 vercel.json 에는 드러나지 않습니다. 위 기록에서 도메인 연결이 Ready 0.24초 뒤에 일어났으니 지금 두 프로젝트에는 걸려 있지 않습니다. 켜더라도 프로젝트마다 따로 기다리므로 화면과 API 의 배포 순서까지 맞춰 주지는 않습니다.

실행 취소의 양면. cancel-in-progress: true 는 같은 group 의 진행 중인 실행을 취소합니다. PR 에서는 이미 낡은 커밋의 검사를 멈춰 시간을 아낍니다. main 의 group 은 ci-refs/heads/main 하나뿐이라, 두 PR 을 짧은 간격으로 병합해 첫 main 실행이 끝나기 전에 두 번째가 시작되면 첫 실행이 취소되고 먼저 병합된 커밋에는 통과 기록이 남지 않습니다. 마지막 실행이 두 변경을 모두 담고 있으므로 검사 자체는 되지만, 실패했을 때 어느 병합에서 깨졌는지 좁히기는 어려워집니다. Vercel 쪽에도 비슷한 규칙이 있지만 방식이 다릅니다. 두 프로젝트가 쓰는 Hobby 플랜은 팀 전체에서 빌드를 한 번에 하나만 돌리고 On-Demand Concurrent Builds 를 쓸 수 없어서, 같은 브랜치의 빌드가 차례로 처리됩니다. Vercel 은 진행 중인 빌드를 취소하지 않고 끝까지 마칩니다. 그동안 쌓인 이전 커밋의 대기 빌드는 건너뛰고 가장 최근 커밋만 빌드해 배포합니다(Vercel 빌드 큐 문서, 2026-10-15 확인). 그래서 첫 병합 커밋은 main CI 실행이 취소되어 통과 기록이 없어도 배포될 수 있습니다. 반대로 빌드가 도는 동안 PR 이 두 개 이상 더 병합되면 그 사이 커밋은 배포되지 않습니다. 그 커밋의 CI 도 다음 병합에 취소됐다면 통과 기록조차 남지 않습니다.

최소 권한. GitHub 은 GITHUB_TOKEN 의 기본 권한을 저장소 내용 읽기로 두고, 필요한 job 에서만 늘리라고 권합니다(GitHub 보안 문서, 2026-10-15 확인). 이 워크플로는 contents: read 하나만 적으므로 적지 않은 나머지 권한은 모두 none 이 되고, secrets. 도 참조하지 않습니다. 그래도 토큰은 있습니다. GitHub 은 job 마다 GITHUB_TOKEN 을 비밀 값으로 만들고, actions/checkout@v4 는 기본값(persist-credentials: true)대로 이 토큰을 러너의 git 설정에 저장했다가 job 이 끝날 때 지웁니다(checkout README, 2026-10-15 확인). 그 사이 같은 job 에서 도는 코드, 곧 uv sync·npm ci 로 받은 의존성과 테스트·빌드 스크립트는 이 토큰을 읽을 수 있습니다. 권한을 읽기 하나로 줄여 두었기 때문에 토큰이 새더라도 할 수 있는 일은 저장소 읽기에 그칩니다.

lockfile 을 그대로 쓰기. uv 0.12.8 의 도움말에 따르면 uv sync 는 --locked 나 --frozen 이 없으면 설치 전에 다시 lock 합니다. --frozen 은 uv.lock 을 그대로 기준으로 삼으므로, CI 는 개발자가 lock 에 고정한 버전을 그대로 설치합니다. 대신 --frozen 은 lock 이 pyproject.toml 과 맞는지 확인하지 않습니다. 그 확인은 --locked 의 일이고, 어긋나면 오류로 멈춥니다. 프런트의 npm ci 는 어긋나면 멈추므로, 지금 두 쪽의 엄격함이 다릅니다.

CI 에 비밀 값이 필요 없는 이유. 테스트가 외부 API 를 부르지 못하게 막는 픽스처가 모든 테스트에 자동으로 붙습니다.

@pytest.fixture(autouse=True) def offline_api_boundary(monkeypatch): """A future real .env key must never turn this test suite into paid traffic.""" import httpx monkeypatch.setattr(settings(), "api_enabled", False) monkeypatch.setattr(settings(), "real_analysis_enabled", False) monkeypatch.setattr(settings(), "share_secret", "") def reject_network(*args, **kwargs): raise AssertionError("Real HTTP requests are forbidden in offline tests") monkeypatch.setattr(httpx.HTTPTransport, "handle_request", reject_network)

  2. docstring 이 목적을 적습니다. 누군가 로컬 .env 에 진짜 키를 넣어도 테스트가 유료 호출이 되면 안 됩니다.
  3. 캐시된 설정 객체의 플래그를 꺼서 실제 분석 경로를 닫습니다. 실제 분석이 필요한 테스트는 자기 픽스처에서 모의 공급자를 끼우고 다시 켭니다.
  4. 공유 서명 키도 비웁니다. PR #28 이 공유 링크를 더하면서 넣은 줄입니다.
  5. 동기 httpx 전송의 handle_request 를 예외로 바꿔, 실제 요청이 나가려 하면 그 테스트가 실패합니다.

보호는 두 겹입니다. 플래그가 유료 경로를 닫고, 전송 차단이 동기 httpx 요청을 막습니다. 비동기 전송(AsyncHTTPTransport)은 바꾸지 않으므로, 전송 차단만으로 모든 네트워크가 막힌다고 말할 수는 없습니다.

원리 노트: 외부 입력은 표현식이 아니라 환경변수로

GitHub 문서에 따르면 run: 명령은 러너의 임시 셸 스크립트로 실행되고, 그 안의 ${{ … }} 는 스크립트가 돌기 전에 평가되어 결과 값으로 치환됩니다. 그래서 PR 을 연 사람이 정하는 값에 셸 문법이 섞여 있으면 그대로 명령이 되는 스크립트 인젝션이 생길 수 있고, 문서는 head_ref 와 브랜치 이름을 신뢰할 수 없는 입력의 예로 듭니다(GitHub 스크립트 인젝션 문서, 2026-10-15 확인). 권하는 방법은 표현식 값을 중간 환경변수에 넣는 것이고, 그러면 값이 스크립트를 만드는 데 쓰이지 않고 변수로만 쓰입니다(GitHub 보안 문서). branch-name job 이 HEAD_REF 와 AUTHOR 를 env: 로 넘기고 스크립트 안에서는 "$HEAD_REF" 처럼 따옴표로 감싼 셸 변수로만 쓰는 이유입니다.

원리: 빌드의 공급망 검사와 설정이 굳는 시점

API 빌드는 인터넷에서 받은 모델을 무엇으로 믿고, 저장소 밖 코드를 어떻게 가져오며, 환경변수를 바꾸면 언제 반영됩니까?

모델 가중치는 저장소에 없고 GitHub Release 에 있습니다. 빌드는 그것을 받아 쓰므로, 받은 바이트가 학습 때 만든 그 바이트인지 확인해야 합니다(공급망 검사). 신뢰의 출발점은 코드에 적힌 두 상수입니다.

ROOT = Path(__file__).parent URL = "https://github.com/C-Designer/kant_project_2/releases/download/model-lovecode-rule5-axes-v1/lovecode-rule5-v5-train4800h-axes-reg.zip" SHA256 = "dde7c4e61ea99f2588b4bc52ec50f90986291801bcf7e0401ec8e6cdb64eb3f6"
  1. "최신 Release" 같은 움직이는 주소가 아니라 특정 태그(model-lovecode-rule5-axes-v1)의 특정 파일입니다.
  2. 그 파일의 SHA-256 입니다. 같은 URL 에서 다른 바이트가 내려오면 30줄에서 빌드가 멈춥니다. URL 이 같다는 것만으로는 내용이 같다는 보장이 없고, 해시가 그 보장을 코드로 만듭니다.

검사는 세 번 일어납니다.

  • ZIP 전체(30줄): 다운로드 경로를 믿지 않아도 됩니다. 실패하면 명시적인 ValueError 입니다.
  • 가중치 파일(43줄): ZIP 안 report.json 의 artifact_sha256 은 학습이 끝날 때 train.py 가 계산해 둔 값입니다(backend/lovecode/train.py:249). 첫 검사를 통과했다면 ZIP 안의 바이트는 이미 확정되므로, 이 검사는 보고서와 가중치가 짝이 맞는지 확인하는 의미가 큽니다. 꺼내는 네 파일 가운데 파일별 해시가 있는 것은 model.safetensors 하나이고(보고서에는 이 파일과 API 가 꺼내지 않는 tfidf_lr.joblib 의 해시가 있습니다), 설정·토크나이저 파일은 ZIP 해시에 기댑니다.
  • 런타임: 인스턴스가 모델을 올릴 때 Classifier 가 가중치 파일을 다시 해시해 model/report.json 과 비교하고, 다르면 MODEL_DIGEST_MISMATCH 로 거절합니다(backend/lovecode/inference.py:32).

37·43줄은 assert 문입니다. Python 은 -O 로 실행하면 assert 문을 빼고 실행하므로(Python 문서) 이 두 검사도 사라집니다. 지금 빌드 명령은 python build_model.py 라 검사가 돌지만, 30줄처럼 raise 로 쓰면 실행 옵션과 상관없이 남습니다.

지우고 고르는 일도 번들 크기와 이어집니다. Vercel 은 Python 함수에 빌드 시점에 닿을 수 있는 프로젝트 파일을 모두 넣고 자동으로 덜어 내지 않는다고 설명합니다(Vercel Python 런타임 문서, 2026-10-15 확인). 그래서 네 파일만 꺼내고 ZIP 은 지웁니다. 가중치 파일 하나가 442,505,216 바이트(약 422 MiB)이고, 같은 문서가 적은 Python 번들 표준 한도는 압축 전 500 MB 입니다. README 는 API 가 CPU BERT 를 담은 Large Functions 베타(VERCEL_SUPPORT_LARGE_FUNCTIONS)를 쓴다고 적고, 같은 문서는 Large Functions 를 켜면 Fluid compute 에서 Python 번들을 5 GB 까지 허용한다(공개 베타)고 설명합니다.

다음은 저장소 밖 코드입니다. API 프로젝트의 Root Directory 는 deploy/vercel 인데 앱 코드는 backend/lovecode 에 있습니다.

def stage_sources(root=ROOT): """Git builds include backend sources outside this project's root directory.""" source = root.resolve().parents[1] / "backend/lovecode" destination = root / "lovecode" if source.is_dir(): if destination.exists(): shutil.rmtree(destination) shutil.copytree(source, destination, dirs_exist_ok=True, ignore=shutil.ignore_patterns("__pycache__", ".env*")) if not (destination / "api.py").is_file(): raise RuntimeError("Backend sources missing; enable sourceFilesOutsideRootDirectory")
  1. deploy/vercel 에서 두 단계 위, 곧 저장소 루트의 backend/lovecode 를 찾습니다.
  2. 지난 빌드의 복사본이 남아 있으면 지웁니다. 백엔드에서 지운 모듈(PR #20 의 db.py 같은)이 배포본에 남지 않게 하려는 것이고, tests/test_vercel_build.py 31~43줄이 확인합니다.
  3. 캐시 폴더와 .env* 는 복사하지 않습니다. 로컬 비밀 파일이 번들에 들어가지 않습니다.
  4. 복사 결과에 api.py 가 없으면, 곧 루트 밖 파일을 읽지 못했으면 고칠 방법이 적힌 오류로 멈춥니다.

Vercel 문서는 Root Directory 를 정하면 앱이 그 밖의 파일에 접근할 수 없다고 설명하고, 프로젝트 설정의 "Include source files outside of the Root Directory in the Build Step" 을 켜면 빌드 단계에서 접근할 수 있다고 안내합니다(모노레포 FAQ, 2026-10-15 확인). 오류 메시지의 sourceFilesOutsideRootDirectory 는 Vercel REST API 의 프로젝트 필드 이름이고, 문서는 이 필드를 루트 디렉터리 밖에 소스 파일이 있는지를 나타내는 값으로 설명합니다(Vercel REST API 문서). main() 이 이 함수를 다운로드보다 먼저 부르므로, 설정이 꺼진 프로젝트는 모델을 받기 전에 실패합니다(fail fast). 참고로 Git 빌드는 backend/lovecode 전체를 복사하고, scripts/prepare_vercel.py 의 수동 패키징만 허용 목록을 씁니다. README 는 자동 배포에 수동 경로를 쓰지 않는다고 적습니다.

main 커밋마다 두 프로젝트가 모두 빌드되는 이유. Vercel 은 모노레포에서 커밋이 건드리지 않은 프로젝트의 빌드를 건너뛰는 기능(Skipping unaffected projects)을 제공하고, 2025-02-24 부터 새 프로젝트에서는 이 기능이 기본으로 켜집니다(Vercel 변경 기록). 문서가 꼽는 "바뀐 프로젝트" 의 조건은 Root Directory 안 소스의 변경, package.json 에 적힌 내부 패키지 의존성의 변경, 그 프로젝트에만 영향을 주는 lockfile 변경이고, npm·yarn·pnpm·Bun 워크스페이스를 써야 한다는 요건이 붙습니다(Vercel 모노레포 문서, 2026-10-15 확인). 이 저장소에는 워크스페이스 정의가 없고, API 가 기대는 backend/lovecode 는 Root Directory(deploy/vercel) 밖이면서 어느 package.json 에도 의존성으로 적혀 있지 않습니다. 그래서 백엔드만 고친 커밋을 Vercel 이 API 프로젝트의 변경으로 본다는 보장이 없습니다. README 는 이 기능을 꺼 두어 백엔드 경로 변경도 배포에 반영한다고 적고, 기능이 꺼져 있으면 커밋마다 연결된 프로젝트가 모두 배포됩니다(같은 문서). 빌드 단계에서 루트 밖 파일을 읽게 하는 설정과 그 파일이 바뀌었을 때 다시 빌드하게 하는 설정은 별개이고, 이 프로젝트는 둘 다 맞춰 두어야 합니다.

main 만 배포하는 규칙의 세부. git.deploymentEnabled 에 적지 않은 브랜치는 기본값이 true 이므로 "**": false 로 먼저 모두 꺼야 합니다. 키는 minimatch 문법이고, 한 브랜치가 여러 규칙에 걸리면 하나라도 true 일 때 배포합니다(Vercel Git 설정 문서). minimatch 에서 foo* 는 foo/bar 에 맞지 않으므로(minimatch README), c-designer/docs-learn-infra 처럼 슬래시가 든 브랜치까지 덮으려면 * 가 아니라 ** 가 필요합니다. Vercel 이 minimatch 를 어떤 옵션으로 쓰는지는 문서에 없으므로, 이것은 minimatch 기본 동작을 기준으로 한 설명입니다.

설정이 굳는 세 시점. 환경변수를 바꿔도 곧바로 반영되지 않는 층이 셋 있습니다.

  • 배포 단위: Vercel 은 환경변수 변경이 이전 배포에는 적용되지 않고 새 배포에만 적용된다고 설명합니다(Vercel 환경변수 문서, 2026-10-15 확인). LC_SHARE_SECRET 을 넣은 뒤 프로덕션을 다시 배포한 이유입니다.
  • 빌드 결과물: API_INTERNAL_ORIGIN 은 next build 때 rewrite 표에 들어가므로 화면 프로젝트를 새로 빌드해야 바뀝니다.
  • 프로세스: 같은 배포 안에서도 settings() 는 lru_cache 로 처음 읽은 값을 붙잡고, create_app 이 입장 한도(세마포어 크기)와 공유 서명 키를 앱을 만들 때 한 번 꺼내 둡니다. 한 인스턴스가 사는 동안 값은 바뀌지 않습니다.

배포 의존성도 짚어 둡니다. API 프로젝트는 루트의 uv.lock 이 아니라 lock 파일이 없는 deploy/vercel/pyproject.toml 의 목록으로 설치하므로, CI 가 테스트한 버전과 운영 버전이 다를 수 있습니다(예: FastAPI 는 uv.lock 에서 0.143.0, 배포 목록에서 0.135.1). torch 는 차이가 더 큽니다. uv.lock 은 Linux 에서 2.11.0+cu128(macOS 는 2.14.1), 배포 목록은 2.9.1+cpu 이고, CI 는 torch 를 아예 설치하지 않으므로 운영의 torch 는 어디서도 테스트되지 않습니다.

원리 노트: 해시 고정은 신뢰를 옮긴다

다운로드한 파일을 해시로 확인하면 "다운로드 경로를 믿는가" 라는 질문이 "그 해시를 적은 코드를 믿는가" 로 바뀝니다. 네트워크, Release 저장소, 중간 캐시 중 어디서 바이트가 바뀌어도 빌드가 멈추지만, 코드의 해시 값을 바꿀 수 있는 사람은 다른 모델을 들여올 수 있습니다. 이 저장소에서 그 코드를 바꾸는 길은 PR 하나뿐이고 룰셋이 그 길을 지키므로, 모델의 신뢰는 결국 PR 과정이 떠받칩니다. 패키지 관리자의 lockfile 해시, 컨테이너 이미지를 다이제스트로 고정하는 것도 같은 원리입니다.
