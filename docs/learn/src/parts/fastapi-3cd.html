Strict 계약: extra="forbid" 와 세 종류의 검증기

입력 모델은 왜 모르는 필드를 거부하고, field_validator 와 model_validator 는 각각 언제 어떤 인자로 호출됩니까?

@field_validator("mbti") 는 아직 인스턴스가 없는 시점, 즉 필드 값 하나를 검증하는 도중에 호출되므로 self 가 아니라 cls 를 받는 클래스메서드(classmethod)여야 합니다. pydantic 2.14 는 첫 인자 이름이 self 면 validator-instance-method 오류로 거부하고, cls 면 @classmethod 를 자동으로 씌웁니다(pydantic/functional_validators.py:506-513, pydantic/_internal/_decorators.py:762-775). 그래서 @classmethod 를 생략해도 동작하지만 이 프로젝트는 읽는 사람을 위해 명시합니다. valid_mbti 는 v.upper() 로 바꾼 값을 돌려주는 정규화 패턴이라 "intp" 를 보내도 모델에는 "INTP" 가 저장됩니다(직접 확인).

동시성 테스트: 단계 분리·FIFO·수용 한도·슬롯 반환

스레드 20개로 동시에 요청을 보내는 테스트는 무엇을 증명하고, Event·Lock·ThreadPoolExecutor 를 어떻게 조합해 타이밍을 통제합니까?

테스트는 진짜 BERT 와 LLM 대신 Classifier 와 Explainer 가짜를 씁니다. 둘 다 threading.Lock 으로 보호한 active/peak 카운터로 동시에 몇 개가 안에 있었는지를 기록합니다. Explainer.explain 은 release 이벤트(threading.Event)가 set 될 때까지 최대 5초 멈추므로, 테스트가 원하는 순간까지 모든 해설 단계를 붙잡아 둘 수 있습니다. Classifier.predict 는 20번째 호출에서 all_called 이벤트를 set 해 분류 20건이 모두 끝났다는 신호를 줍니다.

class Classifier: def __init__(self): self.report = {"dataset": {"text_format": "compact-v5"}} self.lock = threading.Lock() self.active = self.peak = self.calls = 0 self.all_called = threading.Event() def predict(self, text): with self.lock: self.active += 1 self.peak = max(self.peak, self.active) time.sleep(0.01) with self.lock: self.active -= 1 self.calls += 1 if self.calls == 20: self.all_called.set() return "T13" class Explainer: def __init__(self): self.release = threading.Event() self.lock = threading.Lock() self.active = self.peak = 0 def explain(self, *args, **kwargs): with self.lock: self.active += 1 self.peak = max(self.peak, self.active) try: assert self.release.wait(5) return demo_result(), {} finally: with self.lock: self.active -= 1

  2. 카운터는 여러 워커 스레드에서 동시에 바뀌므로 Lock 으로 보호합니다.
  3. peak 는 동시에 안에 있던 최대 개수입니다. 이 값이 곧 단계 한도의 증거가 됩니다.
  4. 20번째 호출에서 신호를 보냅니다. 해설이 막혀 있어도 분류가 끝났는지를 테스트가 알 수 있습니다.
  5. release 가 set 될 때까지 멈춥니다. 5초 안에 풀리지 않으면 assert 가 실패해 테스트가 매달리지 않습니다.
  6. demo_result() 는 유효한 PublicResult 라 응답 모델 검증을 통과합니다.

ThreadPoolExecutor(20) 으로 client.post 를 20번 제출하면 20개 스레드가 각자 portal.call 로 앱을 부르고, 동기 엔드포인트 analyse 는 anyio 워커 스레드(기본 40개 한도)에서 돕니다. all_called.wait(3) 이 참이면 해설이 모두 멈춰 있는데도 분류 20건이 끝났다는 뜻이며, 이것이 BERT 슬롯은 해설을 기다리기 전에 반환한다(service.py:54-60)는 단계 분리의 증명입니다. 그 상태에서 보낸 21번째 요청은 analysis_admission 세마포어(기본 20)가 꽉 차 acquire(blocking=False) 가 즉시 False 를 돌려주므로 ANALYSIS_BUSY 429 와 Retry-After: 5 를 받습니다(api.py:164-165). classifier.peak == 2 와 explainer.peak == 5 는 bert_concurrency 와 explanation_concurrency 기본값이 실제 동시 실행 수를 제한했음을 보여 줍니다.

원리 노트: 스레드 기반 동시성 테스트의 세 도구

threading.Event 는 진행을 멈추고 푸는 스위치로 결정적인 순서를 만들고, threading.Lock 은 공유 카운터를 보호하며, ThreadPoolExecutor 의 Future.result() 는 워커의 반환값과 예외를 메인 스레드로 가져옵니다. Event.wait(timeout) 은 set 되면 True, 시간 초과면 False 를 돌려주므로 assert event.wait(3) 한 줄이 타임아웃과 단언을 겸합니다. 동기 FastAPI 엔드포인트는 진짜 OS 스레드에서 돌기 때문에 이런 표준 라이브러리 동기화 도구가 테스트와 서버 코드 양쪽에서 그대로 통합니다.

흔한 대안인 time.sleep 으로 타이밍을 맞추는 방식은 느리고 머신 부하에 따라 결과가 흔들립니다. 이 테스트들은 Event 로 단계를 명시적으로 붙잡고 풀며 카운터의 최댓값을 숫자로 단언하므로, 동시성 한도가 바뀌면 어느 숫자가 깨졌는지 바로 드러납니다.
