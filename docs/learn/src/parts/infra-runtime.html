같은 프로세스 안의 상태라도 락이 필요한지는 그 상태를 만지는 스레드 수로 갈립니다. 인스턴스가 처음 뜰 때

새 인스턴스가 첫 분석을 처리하기까지 어떤 일이 어떤 순서로 일어나고, 왜 모델은 import 때가 아니라 첫 요청 때 올립니까?

콜드 스타트는 요청이 왔는데 데워진 인스턴스가 없어서 새로 준비하는 지연입니다. 러브코드 API 에서 새 인스턴스의 첫 분석이 겪는 지연은 두 층으로 나뉩니다. 플랫폼이 콜드 스타트로 보는 프로세스 시작과 앱 import, 그리고 플랫폼이 보지 못하는 앱 안의 지연인 첫 ready() 의 BERT 모델 로딩입니다.

1 · 환경변수main.py 가 모델 경로와 스레드 수 1 을 정합니다.
2 · 앱 importsettings() 를 처음 읽고 create_app() 이 상태를 만듭니다. torch 는 아직 없습니다.
3 · 첫 ready()health 나 analyses 가 락 아래에서 가중치 해시를 확인하고 모델을 올립니다.
4 · 데워진 상태이후 ready() 는 락 없이 지나가고 요청마다 추론만 합니다.

  2. 일일 20건은 인스턴스별이며, 재시작과 여러 인스턴스를 합친 비용 상한이 아니라고 밝힙니다.

표의 N 은 앱이 아니라 플랫폼이 정합니다. Vercel 이 Fluid compute 의 구조를 설명한 글(Fluid: How we built serverless servers, 2026-10-15 확인)은 인스턴스가 요청을 더 받을 수 있는지를 CPU·메모리 사용량, 남은 수명, 파일 디스크립터, 이전 요청의 오류·타임아웃 같은 지표로 판단하고, 자원이 가장 많이 남고 동시 요청이 가장 적은 인스턴스로 요청을 보낸다고 적습니다. 이 목록에 앱의 입장 세마포어는 없고, 저장소에도 그 값을 플랫폼에 알리는 코드가 없습니다. 자리가 없으면 앱은 기다리지 않고 바로 429 ANALYSIS_BUSY 를 돌려주는데(api.py:171-172), 이 응답이 위 목록의 "오류" 에 드는지는 문서에 없습니다. 게다가 분석 시간의 대부분은 LLM 응답을 기다리는 소켓 대기라 CPU 지표로는 인스턴스가 한가해 보일 수 있습니다. 그래서 50×N 은 인스턴스가 이미 N 개이고 요청이 고르게 퍼졌을 때의 상한입니다. 인스턴스가 하나인 상태에서 51번째 동시 분석이 같은 인스턴스로 오면, 새 인스턴스가 뜨는 대신 429 를 받을 수 있습니다.

입장 한도를 20 에서 50 으로, 해설 슬롯을 5 에서 50 으로 올린 이유가 여기에 있습니다(TECH_SPEC 15절). 해설은 대부분 OpenAI 응답을 기다리는 시간(호출 1건에 7~14초)이라 자리를 늘려도 인스턴스의 CPU 는 거의 늘지 않고, CPU 보호는 BERT 슬롯 2 가 맡습니다. 앱 한도가 낮으면 플랫폼이 부하를 보고 인스턴스를 늘리기 전에 앱이 먼저 429 로 거절하므로, 앱 한도는 넉넉히 두고 확장은 Fluid compute 에 맡겼습니다.

그렇다면 정말로 전체에 한 번만 걸리는 한도는 무엇일까요. 앱 바깥의 것들뿐입니다.

  • OpenAI 계정 한도. 모든 인스턴스의 해설 호출이 같은 키(LC_API_KEY)를 쓰므로 계정 한도는 전역입니다. 넘으면 그 호출은 실패하고, 재시도가 없으므로 502 PROVIDER_UNAVAILABLE 이 됩니다. 요청 1건이 약 3.5k 토큰(재작성이 붙으면 약 7k)이라 50건이 1분 안에 몰리면 175k~350k TPM 이 필요합니다.
  • Vercel 플랜 한도. 동시성 확장 문서는 Hobby·Pro 에서 함수의 동시성이 최대 30,000 까지 자동 확장되고, 확장은 리전마다 10초당 1,000 동시 실행이라는 버스트 한도를 따르며, 넘으면 503 FUNCTION_THROTTLED 가 난다고 적습니다. 인스턴스 하나의 크기는 Hobby 에서 2 GB / 1 vCPU 로 고정입니다(함수 한도 문서, 모두 2026-10-15 확인). 이 규모에서 30,000 동시성보다 먼저 닿는 것은 Hobby 팀의 월간 포함 사용량입니다. Hobby 플랜 문서는 Active CPU 4 CPU-hrs, Provisioned Memory 360 GB-hrs, 함수 호출 100만 회를 적고, 넘으면 대부분 30일이 지나야 다시 쓸 수 있다고 적습니다. 한도 문서상 이 할당량은 팀 단위라 화면·API 두 프로젝트가 함께 씁니다(README.md:40). Fluid compute 가격 문서에 따르면 LLM 응답을 기다리는 시간은 Active CPU 에 잡히지 않지만, Provisioned Memory 는 인스턴스에 진행 중인 요청이 하나라도 있는 동안 계속 쌓입니다. 2 GB 인스턴스라면 360 GB-hrs 는 요청을 처리 중인 시간으로 180시간입니다. 앞에서 본 것처럼 브라우저가 포기한 뒤에도 스레드가 LLM 호출을 쥐고 있으면 그 시간도 여기에 들어갑니다(모두 2026-10-15 확인).
  • 프로젝트 환경변수. 한도는 아니지만 전역으로 하나인 값입니다. 모든 인스턴스가 같은 LC_SHARE_SECRET 을 읽기 때문에 공유 링크는 어느 인스턴스에서 열어도 검증됩니다.

하나 더 운영에서 확인할 점이 있습니다. IP 버킷의 키는 request.client.host 입니다(api.py:95). 러브코드 코드에는 X-Forwarded-For 를 읽는 부분이 없지만, 이 값을 채우는 서버 쪽은 이 헤더를 읽습니다. uvicorn 설정 문서대로 proxy_headers 는 기본으로 켜져 있고, 연결이 신뢰 주소(기본 127.0.0.1)에서 왔으면 client 주소를 X-Forwarded-For 의 값으로 바꿉니다. Vercel 의 Python 런타임(vercel/vercel 저장소의 vercel-runtime vc_init.py)은 ASGI 앱을 127.0.0.1 에 바인딩한 자체 uvicorn 으로 기본 설정 그대로 띄우므로, 배포본의 client.host 는 Vercel 이 API 프로젝트에 넘긴 X-Forwarded-For 값입니다. Vercel 요청 헤더 문서는 Vercel 앞에 프록시가 있으면 이 헤더를 덮어쓰고 외부 IP 를 넘기지 않는다고 적습니다(모두 2026-10-15 확인). 브라우저 요청은 프런트 프로젝트의 rewrite 를 거쳐 들어오므로, 이 값이 방문자 IP 인지 rewrite 를 수행한 쪽의 주소인지는 저장소만으로 확인할 수 없습니다. 후자라면 여러 방문자가 한 버킷을 나눠 쓰게 되므로 운영 로그로 확인할 항목입니다.

이 구조는 무저장 설계의 결과입니다. 각 한도의 기준과 응답은 네 겹의 제한 에서, 저장소 없이 링크를 공유하는 방법은 공유 링크 단계에서 봤습니다. 얻은 것은 운영할 저장소가 없고, 어느 인스턴스든 어느 요청이든 받을 수 있으며(공유 링크도 서명만 확인하면 됩니다), 인스턴스가 사라져도 잃는 사용자 데이터가 없다는 점(진행 중이던 요청만 실패합니다)입니다. 내준 것은 한도가 인스턴스 수에 비례해 늘어나 전체 비용 상한이 되지 못하고, 재시작하면 카운트와 대기열이 사라지며, 대기열이 인스턴스마다 따로라 먼저 온 요청이 먼저 처리된다는 보장도 인스턴스 안에서만 성립한다는 점입니다. README 는 이 대가를 적고 받아들였습니다(README.md:47-49).

면접에서 한 번에 답한다면 이렇게 정리할 수 있습니다. "API 는 Vercel Function 하나로 배포되고, Fluid compute 가 트래픽에 따라 인스턴스를 늘리고 줄입니다. 인스턴스 하나가 여러 요청을 동시에 받기 때문에 프로세스 안의 세마포어, FIFO 슬롯, 락이 의미가 있습니다. 하지만 인스턴스끼리는 메모리를 공유하지 않아서 동시 50건, IP 당 10분 5회, 하루 20건은 모두 인스턴스별 한도입니다. 동시 50건은 N 개면 동시 50×N 이 상한이지만, 하루 20건과 IP 당 10분 5회는 그 기간에 살았던 인스턴스 수만큼 늘어나 고정된 상한이 없습니다. main 머지마다 재배포되면 카운트도 0 으로 돌아갑니다. 또 N 은 플랫폼이 CPU·메모리 같은 자기 지표로 정하고 앱의 입장 한도 50 은 모릅니다. 그래서 51번째 동시 요청이 다른 인스턴스로 간다는 보장은 없고, 같은 인스턴스로 오면 429 를 받습니다. 전체에 한 번만 걸리는 것은 OpenAI 계정 한도와 Vercel Hobby 팀의 월간 사용량 한도(넘으면 대부분 30일 정지)이고, 공유 링크는 서명으로 검증하므로 어느 인스턴스에서나 열립니다. 저장소를 두지 않는 대신 이 관계를 문서에 적고 받아들였습니다."

원리 노트: 공유하지 않는 설계와 수평 확장

인스턴스끼리 아무것도 공유하지 않는 설계(shared-nothing)는 인스턴스를 늘리기만 하면 처리량이 늘고, 어느 인스턴스가 죽어도 나머지가 영향을 받지 않는다는 장점이 있습니다. 대신 "전체에서 몇 번" 같은 전역 불변식은 지킬 수 없습니다. 각 인스턴스가 자기 몫만 보기 때문입니다. 그래서 수평 확장을 설계할 때는 한도마다 "인스턴스당이어도 되는가, 전역이어야 하는가" 를 먼저 나눕니다. CPU 보호(BERT 슬롯)는 인스턴스당이 맞고, 비용 상한(일일 예산)은 본래 전역이어야 의미가 완전해지는 종류입니다. 러브코드는 이 구분을 알고 비용 상한을 인스턴스당 근사치로 두었습니다.
