Runnable 프로토콜과 | 연산자

RunnableLambda(self._draft_step) | RunnableLambda(self._review_step) 의 | 는 어떤 파이썬 호출로 바뀌고, 그 결과물은 무엇입니까?

러브코드의 해설 파이프라인은 generator.py 의 revise_chain() 한 식으로 조립됩니다. 메서드 세 개와 분기 하나를 | 로 이어 붙인 것이 전부이며, 이 식이 돌려주는 객체를 나중에 .invoke({"text": ..., "type_id": ...}) 로 실행합니다. 이 섹션은 그 | 가 문법이 아니라 메서드 호출이라는 점부터 확인합니다. 체인을 만드는 시점에는 LLM 호출이 전혀 일어나지 않으며, make_llm 조차 _draft_step 안의 self.chain() 이 불릴 때까지 미뤄집니다(198, 266).

return ( RunnableLambda(self._draft_step) | RunnableLambda(self._review_step) | RunnableBranch( (lambda s: bool(s["problems"]), RunnableLambda(self._repair_step)), RunnablePassthrough(), ) )
  1. self._draft_step 은 바운드 메서드(bound method)입니다. RunnableLambda 가 이를 감싸 LangChain 부품으로 만듭니다.
  2. 첫 | 가 평가되는 지점입니다. 왼쪽 객체의 __or__(오른쪽) 이 호출되어 RunnableSequence 가 생깁니다.
  3. 두 번째 | 의 왼쪽은 이미 RunnableSequence 이므로 RunnableSequence.__or__ 가 호출됩니다. 다음 섹션에서 평탄화를 봅니다.
  4. 조건은 순수 람다, 실행부는 RunnableLambda 입니다. 람다는 RunnableBranch 생성자 안에서 coerce_to_runnable 로 포장됩니다.
  5. 기본 가지(default)로 항등 Runnable 인 RunnablePassthrough() 를 둡니다.

이 식의 모든 조각은 같은 추상 클래스 Runnable 을 상속합니다. 프롬프트 템플릿, 채팅 모델, 함수 래퍼, 분기, 병렬 맵이 전부 같은 인터페이스를 가지므로 | 로 이을 수 있고, 조립 결과도 다시 Runnable 이라 .invoke 할 수 있습니다. 설치된 langchain-core 1.6.9 의 클래스 정의 머리 부분입니다.

class Runnable(ABC, Generic[Input, Output]): """A unit of work that can be invoked, batched, streamed, transformed and composed. Key Methods =========== - `invoke`/`ainvoke`: Transforms a single input into an output. - `batch`/`abatch`: Efficiently transforms multiple inputs into outputs. - `stream`/`astream`: Streams output from a single input as it's produced. - `astream_log`: Streams output and selected intermediate results from an input.
  1. Runnable 은 추상 기반 클래스(ABC)이고 Generic[Input, Output] 입니다. 입력·출력 타입이 제네릭 매개변수로 붙습니다.
  2. invoke/ainvoke 는 입력 하나를 출력 하나로 바꿉니다. 러브코드가 쓰는 유일한 실행 메서드입니다.
  3. batch 의 기본 구현은 스레드 풀에서 invoke 를 병렬 호출합니다(932-980).
  4. stream 의 기본 구현은 invoke 결과를 한 번 yield 하는 것입니다(1195-1214).

원리 노트: Runnable 프로토콜은 invoke 하나 위에 세워집니다

하위 클래스가 반드시 구현해야 하는 메서드는 invoke 하나입니다(@abstractmethod, base.py:886). ainvoke 는 기본적으로 run_in_executor 로 invoke 를 스레드에서 돌리고(930), batch 는 스레드 풀로 invoke 를 병렬 호출하며(979-980), stream 은 invoke 결과를 한 번 yield 합니다(1214). 즉 invoke 만 쓰면 나머지 세 메서드를 공짜로 얻고, 진짜 스트리밍이나 배치 API 를 가진 클래스만 이를 덮어씁니다. langchain-core 1.6.9 기준이며, 이 성질은 어떤 프로젝트에서도 같습니다.

a | b 를 만나면 파이썬은 a.__or__(b) 를 호출합니다. 연산자 오버로딩(operator overloading)이지 LangChain 전용 문법이 아니며, 본체는 한 줄입니다.

def __or__( self, other: Runnable[Output, Other] | Callable[[Iterator[Output]], Iterator[Other]] | Callable[[AsyncIterator[Output]], AsyncIterator[Other]] | Callable[[Output], Other] | Mapping[str, Runnable[Output, Any] | Callable[[Output], Any] | Any], ) -> RunnableSerializable[Input, Any]: """Runnable "or" operator. Compose this `Runnable` with another object to create a `RunnableSequence`. Args: other: Another `Runnable` or a `Runnable`-like object. Returns: A new `Runnable`. Raises: TypeError: If `other` cannot be coerced to a `Runnable`. This method does not return `NotImplemented`, to avoid delegating LCEL composition to unrelated reflected `|` implementations. To interoperate, implement `Runnable`, make the object callable, or define `__or__` on the left. """ return RunnableSequence(self, coerce_to_runnable(other))
  1. 파이썬은 a | b 를 a.__or__(b) 로 번역합니다. 왼쪽이 Runnable 이 아니고 오른쪽만 Runnable 이면 __ror__(698-723)가 대신 불립니다.
  2. 오른쪽 피연산자는 Runnable 뿐 아니라 일반 함수, 제너레이터 함수, dict 까지 허용됩니다. 타입 힌트가 그 목록입니다.
  3. 변환이 안 되면 NotImplemented 를 돌려주지 않고 TypeError 를 냅니다. 엉뚱한 객체의 __ror__ 에 조합을 위임하지 않기 위해서입니다.
  4. 오른쪽을 coerce_to_runnable 로 바꾼 뒤 RunnableSequence(self, other) 를 만듭니다. 실행은 아직 없습니다.

오른쪽에 함수나 dict 를 그냥 써도 되는 이유가 coerce_to_runnable 입니다. 러브코드에서는 분기 조건 람다 lambda s: bool(s["problems"]) 가 이 함수를 거쳐 RunnableLambda 가 되고, 상 단계 lc-3-structured 섹션에서 볼 itemgetter("raw") | output_parser 도 같은 길을 탑니다.

def coerce_to_runnable(thing: RunnableLike[Input, Output]) -> Runnable[Input, Any]: """Coerce a `Runnable`-like object into a `Runnable`. Args: thing: A `Runnable`-like object. Returns: A `Runnable`. Raises: TypeError: If the object is not `Runnable`-like. """ if isinstance(thing, Runnable): return thing if is_async_generator(thing) or inspect.isgeneratorfunction(thing): return RunnableGenerator(thing) if callable(thing): return RunnableLambda(cast("Callable[[Input], Output]", thing)) if isinstance(thing, dict): return RunnableParallel(thing) msg = ( f"Expected a Runnable, callable or dict." f"Instead got an unsupported type: {type(thing)}" ) raise TypeError(msg)
  1. 이미 Runnable 이면 그대로 돌려줍니다. RunnableLambda(...), RunnableBranch(...), RunnablePassthrough() 는 모두 이 줄에서 끝납니다.
  2. 제너레이터 함수는 스트리밍용 RunnableGenerator 로 바뀝니다.
  3. 일반 callable 은 RunnableLambda 로 포장됩니다. 분기 조건 람다가 이 줄을 탑니다.
  4. dict 는 RunnableParallel 로 바뀝니다. 같은 입력을 여러 키에 동시에 보내는 맵입니다.
  5. 그 외는 TypeError 입니다.

왜 이렇게 했는가: 러브코드는 단계 함수를 끝에만 덧붙이지 않고 모든 단계를 RunnableLambda(self._xxx_step) 로 명시적으로 감쌉니다. 코드가 보여주는 이유는 하나입니다: 일반 함수에는 __or__ 가 없으므로 첫 단계는 어차피 Runnable 이어야 합니다. 부수 효과로 바운드 메서드의 __name__ 이 Runnable 이름이 되어(4956-4957) 그래프에 _draft_step 처럼 보입니다. 다만 이 프로젝트는 모든 invoke 를 tracing_context(enabled=False) 로 감싸므로 트레이스 가독성은 설계 이유가 아니라 덤입니다. 흔히 쓰는 prompt | llm | some_function 꼴은 끝의 함수를 자동으로 포장해 주지만, 람다를 쓰면 이름이 RunnableLambda 로 뭉뚱그려집니다.

RunnableLambda 가 메서드를 부르는 법과 RunnableBranch 의 if/else

RunnableLambda(self._draft_step) 은 self 를 어떻게 처리하고, RunnableBranch 는 problems 가 비어 있을 때 무엇을 실행합니까?

단계 메서드는 전부 "state dict 를 받아 키를 덧붙인 새 dict 를 돌려주는" 모양입니다. 시그니처는 (self, state) 이지만 바운드 메서드로 넘기므로 LangChain 이 보는 시그니처는 (state) 하나입니다. 실행 확인 결과 inspect.signature(revise_chain().first.func) 는 (state) 이고 func.__name__ 은 _draft_step 입니다.

원리 노트: strict 의 세 가지 값

langchain-openai 1.7.0 docstring(2661-2669)에 따르면 strict=True 는 "모델 출력이 스키마와 정확히 일치함을 보장하고 입력 스키마도 지원 규칙으로 검증", False 는 "검증 없음", None 은 "인자를 모델에 보내지 않음"입니다. 다만 Pydantic 클래스 + Responses API + 비스트리밍 조합에서는 LangChain 이 이 인자를 요청에 쓰지 않고 SDK 가 항상 strict: true 를 보냅니다. dict 스키마를 넘길 때만 strict 가 convert_to_openai_function(schema, strict=strict)(4411-4416)로 반영됩니다. 서버가 strict 를 실제로 어떻게 강제하는지는 네트워크 호출 없이 확인하지 않았습니다.

Pydantic 클래스를 넘기고 dict 스키마를 손으로 쓰지 않은 것은 PublicResult 와 같은 Field 제약을 한 곳에서 선언하기 위해서이며, 직접 호출 어댑터 provider.py 는 같은 스키마를 dict 로 들고 있습니다.
