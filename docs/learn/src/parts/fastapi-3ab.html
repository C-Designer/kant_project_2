ASGI 인터페이스와 uvicorn 이 app 을 부르는 지점

uvicorn 이 받은 HTTP 요청은 어떤 모양으로 FastAPI 앱에 건네지고, 앱은 그 호출을 어디서 처음 받습니까?

이 프로젝트는 uvicorn lovecode.api:app 으로 서버를 띄우고(README.md:23), 배포 진입점 deploy/vercel/main.py:10 도 같은 app 객체를 import 합니다. 두 경우 모두 서버가 찾는 것은 "모듈 안의 app 이라는 이름의 호출 가능 객체"이며, 그래서 api.py:202 가 app = create_app() 을 모듈 수준에 두고 있습니다. 이 객체가 따르는 약속이 ASGI(Asynchronous Server Gateway Interface)입니다.

ASGI 앱은 async def __call__(scope, receive, send) 를 가진 객체입니다. scope 는 요청 메타데이터(메서드, 경로, 헤더, 클라이언트 주소) dict 이고, receive 는 본문 조각을 꺼내는 코루틴, send 는 응답 조각을 밀어 넣는 코루틴입니다. 아래 uvicorn 발췌는 이 세 가지를 만들어 앱을 부르는 바로 그 지점입니다.

원리 노트: ASGI 3 호출 규약

ASGI 는 "서버가 요청마다 scope 와 두 코루틴을 앱에 건네고 앱의 코루틴이 끝날 때까지 기다린다"는 약속입니다. 본문은 receive() 가 돌려주는 {"type": "http.request", "body": ..., "more_body": bool} 메시지의 연속이고, 응답은 send() 에 http.response.start(상태·헤더) 뒤 http.response.body(본문) 를 넣는 식입니다. 미들웨어(middleware)란 같은 서명을 가진 ASGI 앱이 다른 ASGI 앱을 감싼 것이라, 서버 입장에서는 가장 바깥 겹만 보입니다. 이 설명은 uvicorn 0.54.0 과 Starlette 1.7.0 기준입니다.

self.scope = { "type": "http", "asgi": {"version": self.asgi_version, "spec_version": "2.3"}, "http_version": event.http_version.decode("ascii"), "server": self.server, "client": self.client, "scheme": self.scheme, # type: ignore[typeddict-item] "method": event.method.decode("ascii"), "root_path": self.root_path, "path": full_path, "raw_path": full_raw_path, "query_string": query_string, "headers": self.headers, "state": self.app_state.copy(), }
  1. h11 로 요청 줄과 헤더를 파싱한 뒤 요청마다 새 scope dict 를 만듭니다. 이 venv 에는 httptools 가 없어 auto.py:6-11 이 h11 구현을 고릅니다.
  2. self.client 는 소켓 peername 에서 얻은 (host, port) 이며 얻지 못하면 None 입니다. 이것이 api.py:92 의 request.client 가 None 일 수 있는 이유입니다.
  3. 메서드 문자열은 여기서 결정되고, boundary 미들웨어의 request.method 가 그대로 읽습니다.
  4. 경로는 root_path 와 합쳐진 전체 경로입니다. rate limit 의 request.url.path.endswith(...) 가 보는 값입니다.
  5. 헤더는 (이름, 값) 바이트 튜플의 리스트이며, ASGI 규약(헤더 이름은 소문자 바이트)대로 203행이 이름을 소문자로 넣습니다. Starlette 의 Headers 도 조회 키를 lower() 로 바꿔 비교하므로(starlette/datastructures.py:545) request.headers.get("origin") 은 어느 ASGI 서버에서든 대소문자를 가리지 않습니다.

  1. 요청 하나당 RequestResponseCycle 이 만들어지고(237-248행) 이 코루틴이 이벤트 루프 태스크로 띄워집니다(258행).
  2. ASGI 규약 그 자체입니다. app 은 lovecode.api.app 이고, self.receive(522-540행) 와 self.send 가 두 코루틴입니다.

앱 쪽에서 이 호출을 처음 받는 메서드는 FastAPI.__call__(fastapi/applications.py:1197) 이고, 텔레메트리가 꺼져 있으면 곧바로 Starlette 의 __call__ 로 위임합니다(1216행). Starlette 는 첫 요청 때 build_middleware_stack() 으로 양파 모양 스택을 만들어 두고, 이후로는 그 최외곽 객체를 부릅니다.

  1. app.exception_handler(...) 로 등록된 핸들러를 500/Exception 용과 나머지로 나눕니다. 러브코드의 RequestValidationError 핸들러는 나머지 쪽으로 갑니다.
  2. 리스트의 첫 원소가 최외곽입니다. ServerErrorMiddleware 가 모든 것을 감싸므로 어디서 터진 예외든 500 으로 끝납니다.
  3. @app.middleware("http") 로 쌓인 사용자 미들웨어가 가운데 들어갑니다.
  4. ExceptionMiddleware 는 사용자 미들웨어 안쪽입니다. 422 핸들러의 응답이 바깥 미들웨어를 다시 지나는 이유입니다(fa-3-exception).
  5. reversed 로 안쪽부터 감싸므로 index 0 이 가장 바깥이 됩니다.
  6. 스택은 첫 요청 때 한 번만 만들어집니다. 그래서 add_middleware 는 시작 후 호출을 거부합니다(105-106행).

왜 이렇게 했는가: 러브코드는 ASGI 를 직접 다루지 않고 FastAPI 앱 객체 하나를 "서버가 import 할 수 있는 app" 으로만 노출합니다. 팩토리를 둔 이유(테스트마다 새 앱과 새 상태, tests/test_analysis_concurrency.py:70)는 하 단계 fa-1-app 에서 봤으므로 여기서는 모듈 수준 app 쪽만 봅니다. uvicorn 0.54.0 에는 --factory 옵션이 있어 create_app 자체를 가리킬 수도 있지만(uvicorn/main.py:389-392), Vercel 진입점 deploy/vercel/main.py:10 은 명령행이 아니라 from lovecode.api import app 한 줄로 앱을 얻으므로 모듈 수준 이름이 필요합니다. 이 구조의 결과 하나를 알아 두어야 합니다. api.py:202 의 create_app() 은 import 시점에 실행되고, 그 안의 36행(AnalysisService() → service.py:19)과 38행이 settings() 를 부르는데, settings.py:26-28 은 lru_cache 라 그때 읽은 환경변수가 프로세스 내내 고정됩니다. 그래서 main.py:5-8 은 LC_MODELS_DIR 같은 환경변수를 import 문(10행)보다 먼저 넣습니다. 순서를 바꾸면 기본값이 먼저 캐시되어 배포 설정이 무시됩니다.

FastAPI 0.143.0 은 위 Starlette 메서드를 그대로 쓰지 않고 덮어써서 겹을 두 개 더 끼웁니다. 실제 겹 순서와 그 결과는 다음 섹션(fa-3-middleware-order)에서 표로 봅니다.

두 미들웨어의 실제 실행 순서

boundary 가 코드상 먼저 정의되어 있는데, 왜 요청은 response_headers 가 먼저 받고 boundary 의 403 에도 보안 헤더가 붙습니까?

api.py 에는 @app.middleware("http") 가 두 번 나옵니다. 52행의 boundary 는 Origin·Content-Type·본문 크기·IP 버킷을 검사해 조기 응답을 돌려주고, 106행의 response_headers 는 어떤 응답이든 받아 보안 헤더 네 개를 덧붙입니다. 이 데코레이터는 fastapi/applications.py:4788 에서 self.add_middleware(BaseHTTPMiddleware, dispatch=func) 를 부르는 단축 표기이고, add_middleware 는 아래처럼 리스트의 맨 앞에 끼워 넣습니다.

def add_middleware(self, middleware_class: _MiddlewareFactory[P], *args: P.args, **kwargs: P.kwargs) -> None: if self.middleware_stack is not None: # pragma: no cover raise RuntimeError("Cannot add middleware after an application has started") self.user_middleware.insert(0, Middleware(middleware_class, *args, **kwargs))

  2. insert(0, ...) 입니다. 나중에 등록한 미들웨어가 index 0, 곧 더 바깥쪽이 됩니다. 실제 앱에서 app.user_middleware 를 찍어 보면 [response_headers, boundary] 순서입니다.

FastAPI 0.143.0 은 Starlette 의 build_middleware_stack 을 통째로 덮어써서, 사용자 미들웨어 바깥에 ExceptionTelemetryMiddleware 를, ExceptionMiddleware 안쪽에 AsyncExitStackMiddleware 를 추가합니다. 반면 Starlette 1.7.0 의 max_body_size 옵션(74-76행의 RequestBodyLimitMiddleware)은 FastAPI 생성자와 이 스택 어디에도 없어서(grep -c max_body_size fastapi/applications.py 는 0), 러브코드의 api.py:63-70 수동 413 이 유일한 본문 크기 제한입니다.

원리 노트: 안쪽 미들웨어의 조기 반환은 바깥에게 "call_next 의 결과"다

BaseHTTPMiddleware 는 dispatch_func(request, call_next) 가 돌려준 Response 를 send 로 흘려보냅니다. 그 send 는 바깥 미들웨어의 call_next 가 듣고 있는 메모리 스트림이라, 바깥 미들웨어는 "안쪽이 라우터까지 갔다가 왔는지, 중간에 돌아섰는지"를 구분할 수 없고 구분할 필요도 없습니다. 따라서 boundary 가 call_next 를 부르지 않고 403 을 돌려줘도, response_headers 의 response = await call_next(request) 에는 그 403 이 도착합니다. Starlette 1.7.0 의 starlette/middleware/base.py 기준입니다.

send_stream, recv_stream = anyio.create_memory_object_stream[Message]() with recv_stream, send_stream: async with create_collapsing_task_group() as task_group: response = await self.dispatch_func(request, call_next) await response(scope, wrapped_receive, send) response_sent.set() recv_stream.close() if app_exc is not None and not exception_already_raised: raise app_exc
  1. 안쪽 앱이 보낸 응답 메시지를 받을 메모리 스트림 한 쌍입니다. 바깥 미들웨어의 call_next 는 recv_stream 에서 첫 메시지(http.response.start)를 기다립니다(155-176행).
  2. 사용자 함수(boundary 또는 response_headers)가 여기서 호출됩니다. 반환값이 곧 이 겹의 응답입니다.
  3. 응답을 실제 send 로 내보냅니다. 이 send 가 바깥 겹의 send_no_error 이므로 바깥의 call_next 가 그 응답을 받습니다.
  4. 안쪽 앱이 예외를 던졌고 아직 다시 던지지 않았다면 여기서 던집니다. 핸들러 없는 예외가 response_headers 를 건너뛰는 경로입니다.

실제 create_app() 에 Origin: https://example.com 으로 POST 하면 403 응답에 cache-control: no-store 와 x-robots-tag: noindex, nofollow 가 붙어 있고, tests/test_api.py:36-40 는 같은 원리를 415 응답으로 검증합니다. 반대로 핸들러가 없는 예외(예: 엔드포인트 안의 RuntimeError)는 call_next 자체가 예외를 다시 던지므로(base.py:173) response_headers 의 헤더 추가 줄에 도달하지 못하고, 최외곽 ServerErrorMiddleware 가 만든 평문 500 에는 보안 헤더가 없습니다. 이 동작은 테스트 라우트를 하나 더 붙인 실제 앱에서 확인했습니다.

왜 이렇게 했는가: 보안 헤더를 "모든 응답"에 붙이려면 헤더 미들웨어가 가장 바깥 사용자 겹이어야 하고, 그러려면 코드상 마지막에 등록해야 합니다. 결과적으로 러브코드는 boundary 를 먼저, response_headers 를 나중에 등록했기 때문에 헤더 미들웨어가 바깥 겹이 되어 모든 조기 응답에 헤더가 붙습니다. 이 순서를 의도했다고 적은 주석은 api.py 에 없지만, tests/test_api.py:36-40 의 test_early_error_headers 가 이 성질을 고정합니다. 흔한 실수는 헤더 미들웨어를 맨 위에 적어 가장 안쪽으로 만드는 것인데, 그러면 더 바깥 미들웨어의 조기 응답(403, 413, 429)에는 헤더가 빠집니다.

본문 스트림을 직접 소비하고 다시 흘려보내기

boundary 는 왜 request.body() 대신 request.stream() 을 읽고, 왜 끝에 request._body 를 손수 넣어야 엔드포인트가 본문을 받습니까?

POST 요청에서 boundary 는 본문을 청크(chunk) 단위로 읽으며 누적 크기를 셉니다. 40,960 바이트를 넘는 청크를 본 순간 나머지 청크를 더 읽지 않고 413 을 돌려주므로, 거대한 본문이 전부 메모리에 올라오기 전에 거절됩니다. uvicorn 은 소켓에서 읽은 만큼을 http.request 메시지로 나눠 보내기 때문에(h11_impl.py:538, more_body 플래그) 이런 조기 중단이 가능합니다.

if request.method == "POST": if request.headers.get("content-type", "").split(";")[0] != "application/json": return error("INVALID_REQUEST", 415) size = 0 chunks = [] async for chunk in request.stream(): size += len(chunk) if size > 40960: return error("PAYLOAD_TOO_LARGE", 413) chunks.append(chunk) request._body = b"".join(chunks)
  1. Content-Type 의 매개변수(; charset=...) 를 떼고 application/json 인지만 봅니다. FastAPI 자체의 Content-Type 검사(routing.py:441-463)보다 먼저 415 로 끊습니다.
  2. stream() 은 receive() 메시지를 하나씩 꺼내는 비동기 제너레이터입니다. body() 였다면 전체를 모은 뒤에야 길이를 알 수 있습니다.
  3. 40 KiB 초과를 본 즉시 return 합니다. 남은 청크는 읽지 않습니다. tests/test_api.py:10-15 가 42,000 바이트로 이 경로를 확인합니다.
  4. 검사를 통과한 바이트를 _body 에 넣습니다. 이 한 줄이 하류(엔드포인트)로 본문을 재전송하는 스위치입니다.

여기서 주의할 점은 미들웨어의 request 와 엔드포인트의 request 가 다른 객체라는 사실입니다. BaseHTTPMiddleware.__call__ 은 _CachedRequest(scope, receive) 를 만들어 사용자 함수에 넘기고(base.py:106), 안쪽 앱에는 원래 receive 대신 request.wrapped_receive 를 넘깁니다(107행, 149행). 엔드포인트 쪽 Request 는 FastAPI 가 routing.py:142 에서 새로 만들며, 둘을 잇는 통로는 ASGI receive 메시지뿐입니다.

원리 노트: 스트림은 한 번만 흐른다

ASGI 의 receive() 는 큐에서 메시지를 꺼내는 소비형 호출이라, 한 겹이 읽은 본문은 다음 겹이 다시 받을 수 없습니다. Starlette 1.7.0 의 BaseHTTPMiddleware 는 이 문제를 "미들웨어가 body() 로 캐시한 바이트를 하류에 재전송"하는 방식으로 풀고, 캐시 없이 스트림만 소비했다면 빈 본문을 보냅니다. 따라서 미들웨어에서 본문을 검사하려면 body() 를 쓰거나, 러브코드처럼 stream() 으로 센 뒤 _body 를 직접 채워야 합니다. _body 는 밑줄로 시작하는 내부 속성이므로 Starlette 버전이 바뀌면 깨질 수 있는 의존입니다.

왜 이렇게 했는가: body() 한 줄이면 코드는 짧지만, 크기를 알기 전에 전체를 메모리에 올려야 하므로 "큰 본문을 거절한다"는 목적에 어긋납니다. stream() 으로 세다가 끊는 방식은 거절 비용을 40 KiB 로 묶어 주는 대신 _body 를 손수 채우는 책임을 집니다. 다른 흔한 방식은 Starlette 의 max_body_size 나 리버스 프록시의 본문 제한을 쓰는 것인데, 전자는 FastAPI 0.143.0 이 연결해 주지 않고 후자는 배포 구성에 따라 달라지므로 앱 안에 둔 것입니다.

원리 노트: 이벤트 루프는 하나, 블로킹은 스레드로

asyncio 이벤트 루프는 스레드 하나에서 코루틴을 번갈아 실행하므로, 코루틴 안에서 CPU 를 오래 쓰거나 소켓을 동기적으로 기다리면 같은 루프의 다른 모든 요청이 멈춥니다. FastAPI 는 def 엔드포인트를 anyio 워커 스레드로 보내 이 문제를 피하고, 스레드 수는 CapacityLimiter(기본 40) 로 묶습니다. 반면 @app.middleware("http") 의 dispatch 는 항상 코루틴으로 await 되므로(base.py:197) 미들웨어 안의 블로킹은 피할 길이 없습니다. anyio 4.15.1 과 FastAPI 0.143.0 기준입니다.

analyse 를 def 로 둔 이유는 그 안에서 하는 일이 모두 블로킹이기 때문입니다. service.analyse 는 self.classifier.predict(...) 로 CPU BERT 추론을 돌리고(service.py:55), self.explainer.explain(...) 으로 OpenAI 를 동기 SDK 로 호출하며(61행, 최대 45초 타임아웃), 그 전에 StageLimit.acquire 가 threading.Condition.wait 로 최대 30초를 기다립니다(concurrency.py:30). 이것들을 async def 안에서 그대로 부르면 그 시간 동안 health 를 포함한 모든 요청이 응답하지 못합니다.

같은 이유로 threading.BoundedSemaphore, threading.Lock, threading.Condition 같은 표준 동기화 도구가 러브코드에서 그대로 유효합니다. 엔드포인트가 진짜 OS 스레드에서 돌기 때문입니다. 대신 대기 중인 요청 하나가 워커 스레드 하나를 점유하므로, analysis_capacity 의 상한 32(settings.py:19) 와 기본 토큰 40 사이에는 8개의 여유가 남는 수치 관계가 성립합니다. 이 관계가 의도된 것이라는 문구는 저장소에 없으므로 수치만 확인한 것으로 받아들이면 됩니다.

왜 이렇게 했는가: 흔한 대안은 async def analyse 로 쓰고 안에서 await run_in_threadpool(service.analyse, body) 를 직접 부르는 것입니다. 결과는 같지만 블로킹 호출이 하나라도 await 바깥에 남으면 루프가 멈추는 실수를 열어 둡니다. def 로 두면 함수 전체가 스레드에서 돌아 그런 실수가 구조적으로 불가능하고, 검증 코드도 tests/test_analysis_concurrency.py:70-73 처럼 스레드 20개에서 동시에 요청을 보내 확인할 수 있습니다. 가장 흔한 실수는 그 반대인 "async def 안에서 requests.get 이나 모델 추론을 그냥 부르는 것"이며, 이 프로젝트에는 그런 자리가 없습니다.

StageLimit: FIFO 와 기한이 있는 단계별 슬롯

43줄짜리 concurrency.py 는 어떻게 "먼저 온 요청이 먼저 들어가고, 30초를 넘기면 포기하며, 실패해도 슬롯이 새지 않는다"를 보장합니까?

StageLimit 은 세마포어와 비슷하지만 두 가지가 다릅니다. 대기 순서를 deque 로 명시해 FIFO 를 보장하고, 절대 시각 deadline 을 받아 그 시각이 지나면 AnalysisBusy 를 던집니다. 표준 threading.Semaphore 는 깨어나는 순서를 보장하지 않고, 타임아웃은 상대 시간이라 여러 단계가 같은 기한을 공유하기 어렵습니다.

"""Per-instance FIFO stage limits; never hold a BERT slot while waiting for an LLM.""" import threading import time from collections import deque from contextlib import contextmanager class AnalysisBusy(Exception): pass class StageLimit: def __init__(self, capacity): self.capacity = capacity self.active = 0 self.waiters = deque() self.condition = threading.Condition() @contextmanager def acquire(self, deadline): ticket = object() with self.condition: self.waiters.append(ticket) try: while self.waiters[0] is not ticket or self.active >= self.capacity: remaining = deadline - time.monotonic() if remaining <= 0: raise AnalysisBusy() self.condition.wait(remaining) self.waiters.popleft() self.active += 1 self.condition.notify_all() except BaseException: self.waiters.remove(ticket) self.condition.notify_all() raise try: yield finally: with self.condition: self.active -= 1 self.condition.notify_all()
  1. 대기 만료 전용 예외입니다. api.py:178-179 가 429 ANALYSIS_BUSY 로 바꿉니다.
  2. 티켓의 FIFO 큐입니다. 큐의 머리(waiters[0])만 슬롯을 받을 자격이 있습니다.
  3. Condition 은 락과 대기/통지를 묶은 객체입니다. active·waiters 의 모든 변경이 이 락 아래에서 일어납니다.
  4. 두 조건을 함께 봅니다. 슬롯이 비어도 내가 머리가 아니면 기다리고, 머리여도 슬롯이 없으면 기다립니다. 깨어난 뒤 다시 검사하는 while 이므로 허위 기상(spurious wakeup)에도 안전합니다.
  5. Condition.wait(timeout) 은 락을 풀고 잠들었다가 notify_all 또는 시간 만료에 깨어나 락을 다시 잡습니다. 그래서 같은 락 안에서 다른 스레드가 active 를 바꿀 수 있습니다.
  6. AnalysisBusy 뿐 아니라 KeyboardInterrupt 같은 BaseException 에도 티켓을 큐에서 빼고 모두를 깨웁니다. 빠지지 않은 티켓이 머리에 남으면 뒤의 모든 요청이 영원히 막힙니다.

31-33행은 머리 티켓을 빼고 active 를 올린 뒤 notify_all() 을 부릅니다. notify() 로 하나만 깨우면 깨어난 스레드가 새 머리가 아닐 수 있어서, 모두 깨워 각자 26행 조건을 다시 검사하게 하는 쪽이 단순하고 안전합니다. 38-43행은 yield 로 with 블록 본문을 실행한 뒤 finally 에서 active 를 내리고 다시 모두를 깨웁니다. 본문에서 ProviderError 가 나도 finally 는 반드시 실행되므로 슬롯이 새지 않습니다.

원리 노트: 조건 변수(condition variable) 의 세 동작

threading.Condition 은 "락을 잡고 조건을 검사한다 → 조건이 거짓이면 wait() 로 락을 풀고 잠든다 → 누군가 상태를 바꾸고 notify_all() 하면 깨어나 락을 다시 잡고 조건을 재검사한다"는 패턴을 위한 도구입니다. CPython 3.12 의 threading.py:323-369 는 wait() 가 내부 waiter 락을 만들어 큐에 넣고 바깥 락을 풀었다가 복구하는 식으로 구현돼 있고, notify_all() 은 대기 중인 waiter 수만큼 notify() 를 부릅니다(424-431행). wait() 는 반드시 while 안에서 써야 하며, 이 패턴은 프레임워크와 무관하게 성립합니다.

서비스는 이 슬롯을 단계별로 따로 만듭니다. service.py:19-20 에서 BERT 용 StageLimit(2) 와 해설용 StageLimit(5) 를 만들고(settings.py:20-21), analyse 는 아래처럼 두 with 블록을 순서대로 지나갑니다. 핵심은 첫 번째 with 가 끝난 뒤에야 두 번째 with 가 시작된다는 구조입니다.

원리 노트: 프로세스 안 상태의 범위

FastAPI 앱 객체에 묶인 Python 객체(dict, deque, 세마포어)는 그 객체를 만든 프로세스 안에서만 보입니다. uvicorn 을 워커 여러 개로 띄우거나 서버리스 플랫폼이 인스턴스를 늘리면 프로세스마다 별도의 복사본이 생기고, 서로를 알지 못합니다. 전역 상한이 필요하면 Redis 같은 외부 저장소나 로드밸런서·게이트웨이의 제한을 써야 하며, 이것은 프레임워크가 아니라 배포 구조의 문제입니다.

왜 이렇게 했는가: 이 프로젝트는 저장·공유 기능과 DB 를 제거했고(CODE_GUIDE.md:4) 비용 상한의 목적은 "한 인스턴스가 OpenAI 를 과하게 부르지 않게" 하는 것이므로, 외부 저장소 없이 프로세스 안 자료구조로 충분하다고 본 것입니다. 네 겹이 각각 다른 자원(네트워크 남용, 스레드·메모리, CPU 와 외부 API, 비용)을 겨냥하기 때문에 하나로 합치지 않았고, 그 대가로 인스턴스 수에 비례해 상한이 늘어나는 점을 문서에 적어 두었습니다. 흔한 다른 방식은 게이트웨이에서 IP 제한을 하고 앱에는 동시성 제한만 두는 것인데, 러브코드는 배포 환경에 의존하지 않도록 네 겹을 모두 앱 안에 두었습니다.
