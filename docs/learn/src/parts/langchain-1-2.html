LangChain 이 무엇인가: 이 프로젝트가 쓰는 부품과 쓰지 않는 부품

"LangChain 을 쓴다"는 말이 이 저장소에서 정확히 어떤 패키지와 어떤 기능을 뜻하는지 답합니다.

LangChain 은 한 줄로 말하면 "LLM 호출을 레고 블록처럼 이어 붙이는 표준 인터페이스"입니다. 프롬프트 템플릿(prompt template), 채팅 모델(chat model), 파이썬 함수, 조건 분기 같은 부품이 모두 Runnable 이라는 같은 인터페이스를 구현하고, | 연산자로 이어 붙이면 하나의 새 Runnable 이 됩니다. 이 조합 문법을 LCEL(LangChain Expression Language)이라고 부릅니다. 러브코드는 이 문법으로 "초안 작성 → 규칙 검사 → 재작성 → 결과 변환" 체인을 만듭니다.

직접 적는 패키지는 세 개뿐입니다. langchain-core 가 Runnable, 프롬프트 템플릿, 메시지 타입을 제공하고, langchain-openai 와 langchain-ollama 가 각각 OpenAI 와 로컬 Ollama 서버를 같은 채팅 모델 인터페이스(ChatOpenAI, ChatOllama)로 감쌉니다. 상위 패키지 langchain 이나 langgraph 는 의존성 목록에도, 설치 디렉터리에도 없습니다(uv.lock 에 name = "langchain" 단독 항목이 없고, site-packages 의 langchain 계열 디렉터리는 langchain_core, langchain_ollama, langchain_openai 와 langchain-core 가 끌어오는 작은 프로토콜 타입 패키지 langchain_protocol 0.0.19 뿐입니다).

Runnable[Input, Output] 은 제네릭이라 입력도 출력도 dict, 문자열, 튜플 무엇이든 될 수 있습니다. RunnableSequence.invoke 는 마지막 단계의 반환값을 그대로 돌려주므로(langchain-core 1.6.9 base.py:3466-3467) 마지막 단계가 튜플을 반환하면 체인 결과도 튜플입니다. 러브코드 체인이 dict 로 시작해 (PublicResult, meta) 튜플로 끝나는 이유입니다.

왜 LLM 에게 분류까지 맡기지 않았을까요? 분류는 규칙 라벨로 학습한 BERT 가 재현 가능하게 처리하고 자유 서술만 LLM 에 맡기면, "유형이 왜 이것이냐"의 책임이 분류기 하나로 모이고 해설 모델을 바꿔도 유형 분포가 흔들리지 않습니다. 반대 방향(LLM 이 유형도 고르는 방식)은 provider.py 의 label() 로 남아 있으며 분류 모드가 local 이 아닐 때 쓰입니다(service.py:57-59). 주의할 점은 settings.py:14 의 기본값이 openai 라는 것입니다: 아무 설정 없이 띄우면 LLM 이 유형을 고르고, README 의 배포 환경변수(70행)와 로컬 .env 안내(89행)가 LC_CLASSIFIER_MODE=local 로 BERT 를 켭니다. 어느 모드든 해설기는 이미 정해진 type_id 를 받기만 하며, 중 단계 lc-2-provider 에서 자세히 봅니다.

원리 노트: 앞 단계 출력이 뒤 단계 입력

LCEL 의 RunnableSequence 는 단계들을 순서대로 invoke 하고 각 단계의 반환값을 그대로 다음 단계의 입력으로 넘깁니다. 그래서 이웃한 단계끼리 출력 타입과 입력 타입이 맞물려야 하며, 러브코드는 모든 단계가 state dict 를 주고받다가 마지막 단계만 튜플을 돌려주도록 맞춰 두었습니다. 이 성질은 프로젝트와 무관하게 LangChain 전반에서 성립합니다.

explain_chain() 은 "시퀀스 안의 시퀀스"가 아니라 네 단계짜리 한 시퀀스입니다. 오프라인에서 .steps 를 찍어 보면 [RunnableLambda, RunnableLambda, RunnableBranch, RunnableLambda], 이름은 ['_draft_step', '_review_step', 'RunnableBranch', 'RunnableLambda'] 로 확인됩니다. 바운드 메서드를 감싼 단계는 메서드 이름이 그대로 보이고, 마지막 람다는 RunnableLambda 로 뭉뚱그려집니다.

왜 파이썬 함수 세 개를 차례로 호출하는 대신 체인으로 묶었을까요? 코드가 밝히는 이유는 하나입니다: 분류기를 앞에 붙인 analysis_chain()(generator.py:351-360)이 같은 explain_chain() 을 재사용합니다(모듈 docstring 9행). 각 단계가 콜백 트리의 자식 run 이 되어 추적 도구에서 단계별 시간을 볼 수 있다는 것은 LCEL 의 일반 성질이지만, 이 프로젝트는 모든 invoke 를 tracing_context(enabled=False) 로 감싸므로(238, 338, 345, 366행) 그 이점은 쓰지 않습니다. if 문 하나면 될 분기를 RunnableBranch 로 쓴 대가는 람다 조건식이 조금 낯설다는 점뿐이며, 중 단계 lc-2-steps 에서 분기와 각 단계 함수를 자세히 봅니다.

make_llm(backend, model) 은 백엔드 문자열에 따라 ChatOllama 또는 ChatOpenAI 를 만듭니다. 둘 다 langchain-core 의 BaseChatModel 을 상속한 채팅 모델이라 invoke, with_structured_output 같은 메서드의 겉모양이 같고, 그래서 chain() 은 어느 쪽이 들어오든 같은 프롬프트와 같은 Explanation 스키마를 붙일 수 있습니다(generator.py:197-202).

_call: 한 번의 LLM 호출을 (parsed, meta) 로 바꾸기

chain.invoke 한 번의 결과가 어떻게 성공·실패 코드와 실행 기록으로 정리되는지 답합니다.

_call(chain, inputs) 은 체인을 한 번 실행하고 (parsed dict 또는 None, meta) 를 돌려줍니다. 실패는 예외가 아니라 meta["error"] 코드로 표현되며 세 종류입니다: 네트워크·HTTP·SDK 예외는 PROVIDER_REQUEST_FAILED, 응답은 왔지만 status 가 completed 가 아니면 INCOMPLETE_RESPONSE, 파싱 오류가 있거나 parsed 가 None 이면 SCHEMA_REJECTED 입니다. 성공이면 Pydantic 인스턴스를 model_dump() 로 dict 로 바꿔 돌려주므로(256) 뒤 단계는 dict 키로만 접근합니다.

Returns (parsed dict or None, meta); meta["error"] names a failure.""" meta = self._meta() start = time.perf_counter() try: # Request bodies must not be exported even if a shell enables LangSmith tracing. with tracing_context(enabled=False): out = chain.invoke(inputs) except Exception: # noqa: BLE001 - any provider/network/parser error maps to one code # No prompts, responses or credentials in errors. meta.update( error="PROVIDER_REQUEST_FAILED", elapsed_seconds=time.perf_counter() - start ) return None, meta meta["elapsed_seconds"] = time.perf_counter() - start meta["usage"] = dict(getattr(out.get("raw"), "usage_metadata", None) or {}) response_meta = getattr(out.get("raw"), "response_metadata", {}) if response_meta.get("status", "completed") != "completed": meta["error"] = "INCOMPLETE_RESPONSE" return None, meta parsed = out.get("parsed") if out.get("parsing_error") is not None or parsed is None: meta["error"] = "SCHEMA_REJECTED" return None, meta return parsed.model_dump(), meta

세 단계 함수: _draft_step, _review_step, _repair_step 과 checks.find_problems

state dict 가 단계마다 어떻게 갱신되고, 언제 재작성이 일어나며 무엇이 기록되는지 답합니다.

세 메서드는 모두 state dict 를 받아 {**state, ...} 로 새 dict 를 만들어 돌려줍니다. 받은 dict 를 제자리에서 고치지 않으니 앞 단계의 입력이 뒤에서 바뀌는 일이 없고, 각 단계의 출력이 콜백에 그대로 기록되어도 안전합니다. _draft_step 은 parsed 와 meta 를, _review_step 은 problems 를 더합니다.

  2. 정상 파싱이면 checks.py 의 규칙 검사. 반환값은 (kind, instruction) 쌍 리스트입니다.

  6. 수리 뒤 _review_step 을 다시 불러 problems 를 재계산합니다. _finalize 가 '남은 문제'를 볼 수 있는 이유입니다.

_review_step 의 첫 분기가 핵심입니다. 직전 호출이 PROVIDER_REQUEST_FAILED 였다면 문제 목록을 비워 재시도를 막습니다. 네트워크나 제공자 쪽 장애는 두 번째 호출도 실패할 가능성이 높고, max_retries=0 으로 SDK 재시도까지 끈 상태라 "실패는 바로 실패로 보고"가 일관된 정책입니다. 반대로 응답은 왔지만 형식이 깨졌거나(parsed is None) 규칙에 걸린 경우에는 고칠 거리가 분명하므로 한 번만 재작성합니다. 테스트가 이 구분을 호출 횟수로 확인합니다: 200/429/500 은 1회, incomplete/refusal/invalid 는 2회(tests/test_langchain_web.py:78).

_repair_step 은 두 호출을 하나의 기록으로 합칩니다. elapsed_seconds 와 usage 의 세 토큰 키를 첫 호출 값과 더하고, repair.reasons 에는 검사 종류만 정렬해 넣습니다. 검사 규칙은 checks.py 의 find_problems(parsed, type_id, input_text) 하나에 모여 있고 (kind, instruction) 쌍의 리스트를 돌려줍니다. kind 는 로그와 판정용 짧은 이름이고, instruction 은 REPAIR 프롬프트의 {problems} 자리에 들어갈 "무엇을 고치라"는 문장입니다. 한 구조로 두 소비자(로그와 LLM)를 만족시키는 설계입니다. 발췌한 네 검사 뒤에는 반대 극 단어(opposite_pole, 52-58), 입력에 없는 관계어(fabricated_relations, 59-64), 단정·우열 표현(assertive, superiority, 65-68)이 이어지며 이 넷은 보고 대상이지 거절 기준이 아닙니다.

  2. 필드별 길이 상한(summary 120, 나머지 180)을 넘긴 값마다 length 문제를 하나씩 만듭니다. 지시문에 실제 글자 수가 들어갑니다.

RunnableBranch 는 (조건, 실행) 쌍들과 마지막 기본 가지로 만들어지며(langchain-core 1.6.9 branch.py:101-136), invoke 는 조건을 순서대로 실행해 첫 참인 가지를 고르고 모두 거짓이면 기본 가지를 실행합니다. 러브코드의 조건은 lambda s: bool(s["problems"]), 참이면 _repair_step, 거짓이면 입력을 그대로 돌려주는 RunnablePassthrough()(passthrough.py:233)입니다. _finalize: 남은 문제를 판정해 PublicResult 를 만들거나 ProviderError 를 던지기

체인의 마지막 단계가 어떤 기준으로 결과를 내보내거나 거부하고, 그 거부가 HTTP 502 가 되는 경로를 답합니다.

_finalize(state, limitations) 는 먼저 meta["remaining_problems"] 에 남은 검사 종류를 기록합니다. 그다음 두 가지 이유로 ProviderError 를 던집니다: 호출 자체가 실패했으면 PROVIDER_REQUEST_FAILED, 파싱된 결과가 없거나 남은 문제 중 HARD 집합에 속하는 것이 있으면 OUTPUT_REJECTED 입니다. 둘 다 같은 예외 클래스(provider.py:11-12)이지만 메시지 문자열로 원인을 구분합니다.

원리 노트: 예외는 체인을 그대로 통과합니다

LCEL 의 컨테이너 Runnable(Sequence, Branch, Lambda)은 예외를 삼키지 않습니다. langchain-core 1.6.9 의 _call_with_config(base.py:2315)와 RunnableSequence.invoke(3462-3464)는 except BaseException 에서 on_chain_error 를 부르고 raise 합니다. 예외를 데이터로 바꾸고 싶으면 with_fallbacks 나 with_retry 를 명시적으로 붙여야 하며, include_raw=True 가 바로 그 예입니다. 그래서 러브코드는 "LLM 호출 실패는 데이터(meta)로, 계약 위반은 예외로" 두 층을 나눠 씁니다.

왜 502 일까요? 503 ANALYSIS_UNAVAILABLE 은 설정·모델 로딩 문제(ValueError/OSError/KeyError)에, 502 PROVIDER_UNAVAILABLE 은 "우리 서버는 정상인데 업스트림 생성이 실패"한 경우에 씁니다. 흔한 대안인 500 하나로 뭉뚱그리기와 달리 운영자는 상태 코드만으로 어느 쪽을 봐야 할지 알 수 있고, 사용자에게는 두 경우 모두 내부 정보를 담지 않은 고정 문구만 나갑니다. 테스트는 실패 시 502 와 함께 응답에 내부 문자열이 없음을 확인합니다(tests/test_langchain_web.py:84-85).

원리 노트: 채팅 모델 통합 패키지가 맡는 네 층

langchain-openai 같은 통합 패키지는 (1) 생성자 인자와 메시지 리스트를 제공자별 요청 본문으로 바꾸고, (2) 구조화 출력 스키마를 제공자 형식으로 변환해 붙이고, (3) 응답을 공통 AIMessage(content, usage_metadata, response_metadata)로 되돌리고, (4) 그 위에서 파서와 fallback 을 Runnable 로 조합합니다. 이 네 층 덕분에 호출하는 코드는 제공자를 몰라도 되지만, 그 대가로 요청이 정확히 어떻게 생겼는지는 라이브러리 소스나 테스트의 요청 본문 단언으로 확인해야 합니다. 예를 들어 max_tokens 가 max_output_tokens 로 바뀌는 것은 소스를 열어야 보입니다(base.py:3816-3817, 4622-4624).

트레이드오프를 면접용으로 정리하면 이렇습니다. 직접 호출은 의존성이 httpx 하나뿐이고 요청이 눈에 다 보이지만, 백엔드를 바꾸거나 여러 턴의 대화(수리 프롬프트의 ("ai", "{previous}"))를 다루려면 직렬화 코드를 직접 늘려야 합니다. LangChain 은 그 작업을 맡는 대신 버전마다 내부 경로가 바뀔 수 있으므로, 이 프로젝트처럼 "SDK 는 진짜, 네트워크만 가짜"인 테스트(tests/test_langchain_web.py:61-62)로 요청 본문을 고정해 두는 것이 안전합니다.
