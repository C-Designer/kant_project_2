FastAPI 는 무엇이고, 이 저장소에서 어디까지 맡는가

러브코드의 HTTP 입구를 이루는 FastAPI, Starlette, Pydantic, uvicorn 은 각각 무슨 일을 합니까?

FastAPI 는 Python 으로 HTTP API 를 만드는 웹 프레임워크(web framework)입니다. 설치된 소스를 열어 보면 class FastAPI(Starlette): 한 줄이 보이는데, FastAPI 는 Starlette 이라는 ASGI 프레임워크를 상속한 클래스입니다. Starlette 이 라우팅(routing), 미들웨어(middleware), 요청·응답 객체를 제공하고, FastAPI 는 그 위에 Pydantic 기반의 입력 검증과 OpenAPI 문서 생성을 얹습니다. 이 저장소의 .venv 에 설치된 버전은 fastapi 0.143.0, starlette 1.7.0, pydantic 2.14.0 입니다.

네 번째 조각은 uvicorn 입니다. FastAPI 앱은 스스로 포트를 열지 못하며, README 의 실행 명령 uv run uvicorn lovecode.api:app --host 127.0.0.1 --port 8100 처럼 ASGI 서버(ASGI server)인 uvicorn 이 소켓을 열고 HTTP 를 파싱한 뒤 앱을 호출합니다. uvicorn 이 전화를 받는 쪽이고, FastAPI 앱은 대답하는 쪽입니다. pyproject.toml 의 의존성 목록에서 이 네 조각이 어떻게 선언되는지 먼저 봅니다.

dependencies = [ "fastapi>=0.115,<1", "uvicorn>=0.34,<1", "pydantic-settings>=2.7,<3", "httpx>=0.28,<1", "python-dotenv>=1,<2", "lunar-python>=1.4,<2", "scikit-learn>=1.6,<2", "joblib>=1.4,<2", "tzdata>=2024.1", "torch>=2.7", "transformers>=4.46,<6", "langchain-core>=0.3,<2", "langchain-ollama>=0.3,<2", "langchain-openai>=0.3,<2", ]
  1. 웹 프레임워크 본체입니다. <1 로 메이저 버전을 묶었고, uv.lock 이 실제로는 0.143.0 을 고정합니다.
  2. ASGI 서버입니다. 로컬 개발과 README 의 실행 명령이 이 패키지를 씁니다.
  3. 설정 파일·환경변수를 읽는 pydantic-settings 입니다. pydantic 본체는 fastapi 의 의존성으로 함께 설치되므로 따로 적지 않았습니다.
  4. httpx 는 provider.py 가 OpenAI 를 직접 부를 때 쓰는 HTTP 클라이언트입니다. 테스트용 TestClient 는 Starlette 1.7.0 에서 별도 패키지 httpx2 위에 올라가 있는데, 이 차이는 상 단계에서 자세히 봅니다.
  5. 여기서부터 세 줄은 LangChain 트랙의 재료이며 FastAPI 와는 독립적입니다.

이 네 조각이 만나는 접점이 ASGI(Asynchronous Server Gateway Interface)입니다. uvicorn 은 요청 하나마다 메타데이터 사전 scope 와 두 개의 코루틴 receive, send 를 만들어 앱 객체를 함수처럼 호출합니다. 그 호출을 처음 받는 것은 FastAPI 가 오버라이드한 FastAPI.__call__(applications.py:1197)이며, 텔레메트리가 꺼져 있으면 아래 Starlette 의 __call__ 로 곧바로 위임합니다(1216-1217행).

async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None: scope["app"] = self if self.middleware_stack is None: self.middleware_stack = self.build_middleware_stack() await self.middleware_stack(scope, receive, send)
  1. 앱 객체가 호출 가능한 이유입니다. scope, receive, send 세 인자가 ASGI 약속의 전부입니다.
  2. 요청 범위에 앱 자신을 넣어 두어, 하류의 Request 객체가 request.app 으로 접근할 수 있게 합니다.
  3. 미들웨어 스택은 첫 요청이 올 때 한 번만 조립됩니다. 그래서 앱이 시작된 뒤에는 미들웨어를 추가할 수 없습니다.
  4. 조립된 스택의 가장 바깥 겹에 호출을 넘깁니다. 라우터는 이 양파의 한가운데에 있습니다.

원리 노트: ASGI 와 FastAPI 의 층 구조

ASGI 는 "서버가 scope(요청 메타데이터)와 receive(본문을 꺼내는 코루틴), send(응답 조각을 보내는 코루틴)를 앱에 건네고 앱이 끝날 때까지 await 한다"는 약속입니다. uvicorn 0.54.0 은 요청마다 scope 를 만들어 await app(scope, receive, send) 를 부르며, 이 venv 에는 httptools 가 없어 h11 파서가 선택됩니다. FastAPI 0.143.0 은 Starlette 1.7.0 의 하위 클래스라서 이 호출 규약을 그대로 물려받고, 자신은 Pydantic 검증과 OpenAPI 스키마 생성을 더합니다.

이 프로젝트에서 FastAPI 가 맡는 범위는 HTTP 입구뿐입니다. docs/CODE_GUIDE.md 는 저장형 공유 백엔드와 DB 의존성을 제거했고 결과는 현재 화면에만 남는다고 못 박으며, service.py 첫 줄의 docstring 도 원본 입력을 절대 저장하지 않는다고 선언합니다. 공유 링크도 서명된 결과를 링크 안에 담는 방식(share.py)이라 서버에는 아무것도 남지 않습니다. 그래서 api.py 에는 ORM 도, 세션도, 저장 호출도 없고 검증·제한·오류 응답만 있습니다.

왜 이렇게 나눴을까요. FastAPI 에게 맡긴 일은 "HTTP 바이트를 검증된 Python 객체로 바꾸고, Python 객체를 JSON 으로 돌려보내는 것"뿐이고, 모델 로딩과 LLM 호출은 프레임워크를 전혀 모르는 일반 클래스 AnalysisService 가 맡습니다. 덕분에 테스트는 create_app(analysis_service=service) 로 가짜 서비스를 끼워 넣어 HTTP 층만 따로 검증할 수 있습니다. 핸들러 안에서 모델을 직접 부르는 흔한 초기 구조와 비교하면, 프레임워크 교체나 CLI 재사용이 쉬워지는 대신 파일이 하나 더 늘어납니다.

확인: pyproject.toml:6, fastapi/applications.py:48, starlette/applications.py:92, docs/CODE_GUIDE.md:4, backend/lovecode/service.py:1

create_app 팩토리와 모듈 끝의 app = create_app()

앱 객체는 어디서 어떻게 만들어지고, uvicorn 과 Vercel 은 어떤 이름으로 그것을 찾습니까?

api.py 는 앱을 모듈 전역에서 바로 만들지 않고 create_app() 이라는 팩토리 함수(factory function) 안에서 만듭니다. 함수 안에서 서비스 객체, 공유 링크 코덱, 입장 세마포어, 일일 예산, 레이트리밋 버킷처럼 "앱 한 개당 하나"여야 하는 상태를 지역 변수로 만들고, 그 아래에서 정의하는 미들웨어와 핸들러가 클로저(closure)로 이 변수들을 붙잡습니다. 함수가 끝나도 변수들은 핸들러와 함께 살아남습니다.

def create_app(analysis_service=None, share_codec=None): service = analysis_service or AnalysisService() shares = share_codec or ShareCodec.from_settings() # Bound total in-flight work; the service independently limits each expensive stage. analysis_admission = threading.BoundedSemaphore(settings().analysis_capacity) budget_lock = threading.Lock() budget = {"day": "", "count": 0} app = FastAPI( title="러브코드 로컬 MVP", version="0.2.0", openapi_url="/api/v1/openapi.json", docs_url="/api/docs", ) buckets = defaultdict(deque) salt = secrets.token_bytes(32) salt_time = time.monotonic()
  1. 두 인자 analysis_service, share_codec 은 테스트가 가짜 객체를 주입하는 통로입니다. 기본값 None 이면 다음 두 줄에서 실제 객체를 만듭니다.
  2. 동시 분석 입장권입니다. settings() 를 여기서 한 번 읽어 세마포어 크기를 고정하므로, 테스트가 이 값을 바꾸려면 create_app() 호출 전에 바꿔야 합니다.
  3. 일일 예산은 날짜 문자열과 카운트를 담은 사전 하나입니다. DB 가 없으므로 프로세스가 재시작되면 0 으로 돌아갑니다.
  4. 앱 객체를 만드는 순간입니다. title 과 version 은 OpenAPI info 에 들어가고, title 은 Swagger UI·ReDoc 페이지 제목에도 쓰입니다(applications.py:1168, 1192). 라우팅이나 검증에는 영향이 없습니다.
  5. 기본값 /openapi.json 과 /docs 를 /api/v1/openapi.json, /api/docs 로 옮겼습니다. 백엔드 경로를 모두 /api 아래 모아야 Next.js 프록시가 한 규칙으로 넘길 수 있습니다.
  6. 레이트리밋 해시에 섞을 32 바이트 난수와 그 생성 시각입니다. 타이머는 없고, 레이트리밋이 켜진 요청이 들어왔을 때 마지막 교체로부터 600 초가 지났으면 미들웨어가 버킷을 비우며 교체합니다(api.py:77-81).

FastAPI(...) 생성자는 받은 openapi_url 과 docs_url 에 라우트를 직접 등록합니다. 설치 소스의 setup() 을 보면 openapi_url 에는 스키마 JSON 을 돌려주는 라우트를, docs_url 에는 CDN 의 Swagger UI 를 불러오는 HTML 라우트를 add_route 로 붙입니다. 프로젝트가 건드리지 않은 redoc_url 은 기본값 /redoc 그대로라서, 실제 앱에 GET /redoc 을 보내면 200 이 돌아옵니다. 문서 경로 두 개만 바꾸고 세 번째를 잊은 셈인데, 노출을 막고 싶다면 redoc_url=None 을 넘겨야 합니다.

함수의 마지막 줄과 모듈의 마지막 줄을 같이 봅니다. 팩토리는 완성된 앱을 돌려주고, 모듈 끝에서 그 결과를 전역 이름 app 에 담습니다. README 의 실행 명령에 적힌 lovecode.api:app 은 "lovecode.api 모듈을 import 해서 app 속성을 꺼내라"는 uvicorn 의 표기이므로, 이 한 줄이 없으면 서버가 뜨지 않습니다.

return app app = create_app()
  1. 미들웨어와 핸들러가 모두 등록된 앱을 돌려줍니다. 호출할 때마다 새 세마포어·새 버킷을 가진 독립된 앱이 나옵니다.
  2. 모듈이 import 되는 순간 실행됩니다. 그 안에서 settings() 가 처음 호출되어 환경변수를 읽으므로, 환경변수는 이 import 보다 먼저 준비돼 있어야 합니다.

Vercel 배포 진입점은 그 순서를 이용합니다. deploy/vercel/main.py 는 모델 디렉터리와 스레드 수 환경변수를 먼저 고정한 뒤에야 같은 app 을 import 합니다. settings() 가 lru_cache 로 첫 결과를 붙잡아 두기 때문에, import 뒤에 환경변수를 바꿔도 앱은 알아채지 못합니다.

"""Vercel entrypoint: CPU BERT and OpenAI explanation, with no result database.""" import os from pathlib import Path os.environ["LC_MODELS_DIR"] = str(Path(__file__).parent / "model") os.environ["OMP_NUM_THREADS"] = "1" os.environ["MKL_NUM_THREADS"] = "1" os.environ["TOKENIZERS_PARALLELISM"] = "false" from lovecode.api import app # noqa: F401
  1. LC_MODELS_DIR 을 이 파일 옆의 model 폴더로 고정합니다. settings.py 의 env_prefix="LC_" 때문에 이 이름이 models_dir 필드로 들어갑니다.
  2. PyTorch 와 토크나이저의 스레드 수를 1 로 묶습니다. 서버리스 함수의 작은 CPU 에 맞춘 값이며 FastAPI 와는 무관합니다.
  3. 환경변수가 모두 준비된 뒤에 같은 앱을 가져옵니다. 이 줄의 목적은 import 자체이므로, 사용하지 않는 import 를 지적하는 ruff 규칙 F401 을 noqa 로 끕니다.

원리 노트: 앱 팩토리와 생성자 인자

모듈 전역에 app = FastAPI() 를 두고 전역 변수로 상태를 들고 있는 구조가 가장 흔하지만, 그러면 테스트마다 상태가 공유됩니다. 팩토리 함수는 호출할 때마다 새 앱과 새 상태를 만들어 주고, 인자로 의존성을 바꿔 끼울 수 있습니다. FastAPI 0.143.0 의 생성자는 openapi_url(기본 /openapi.json), docs_url(기본 /docs), redoc_url(기본 /redoc)을 받아 setup() 에서 라우트로 등록하며, None 을 넘긴 것만 빠집니다.

왜 팩토리일까요. tests/test_analysis_concurrency.py 는 create_app(analysis_service=service) 로 가짜 분류기와 해설기를 끼운 앱을 테스트마다 새로 만들고, tests/conftest.py 도 TestClient(create_app()) 로 매번 새 앱을 씁니다. 세마포어·예산·버킷이 앱마다 독립이라 테스트가 서로를 오염시키지 않습니다. 한 가지 주의할 점은 배포본 deploy/vercel/pyproject.toml 이 fastapi 0.135.1 을 고정하고 있어, 이 페이지가 인용하는 라이브러리 줄 번호는 로컬 .venv 의 0.143.0 기준이라는 것입니다.

다섯 개의 엔드포인트와 데코레이터가 하는 일

@app.get 과 @app.post 는 함수와 URL 을 어떻게 묶고, 각 엔드포인트는 무엇을 돌려줍니까?

러브코드 백엔드의 공개 엔드포인트(endpoint)는 다섯 개뿐입니다. 실제 앱의 /api/v1/openapi.json 을 열어 보면 paths 에 정확히 이 다섯 경로만 나열됩니다. 앞의 네 개가 분석 흐름을 이루고, 마지막 GET /api/v1/shared 는 공유 링크를 열 때만 쓰입니다. 공유 경로도 같은 @app.get 데코레이터로 등록되며(backend/lovecode/api.py:207), 아무것도 저장하지 않고 링크에 담긴 서명과 내용만 확인합니다.

메서드경로역할응답
GET/api/v1/health분석 준비 상태 점검status, analysis_ready, demo_ready, provider, verification_mode, share_ready, reason 을 담은 JSON
GET/api/v1/taxonomy16 가지 관계 유형 사전T01~T16 키마다 axes 와 label

가장 단순한 두 핸들러를 봅니다. 데코레이터(decorator) 한 줄이 "이 경로로 이 메서드의 요청이 오면 이 함수를 불러라"는 등록이고, 함수가 돌려주는 dict 는 FastAPI 가 JSON 으로 바꿉니다.

@app.get("/api/v1/health") def health(): ready = service.ready() return { "status": "ok", "analysis_ready": ready, "demo_ready": settings().demo_enabled, "provider": "openai", "verification_mode": service.provider.transport is not None, "share_ready": shares.ready, "reason": "configured_not_quality_certified" if ready else "configuration_required", } @app.get("/api/v1/taxonomy") def taxonomy(): return TAXONOMY
  1. GET 메서드와 경로를 아래 함수에 묶습니다. 경로 문자열은 /api/v1 접두를 포함한 전체 경로입니다.
  2. async 가 없는 일반 def 입니다. FastAPI 는 이런 핸들러를 워커 스레드에서 실행하므로, 안에서 느린 작업을 해도 이벤트 루프가 멈추지 않습니다.
  3. service.ready() 는 설정을 확인하고 필요하면 분류기 모델을 처음 로딩합니다. 느릴 수 있는 호출이라 동기 핸들러가 적합합니다.
  4. dict 를 그대로 돌려줍니다. response_model 이 없으므로 FastAPI 는 검증 없이 JSON 으로 직렬화만 합니다.
  5. verification_mode 는 provider 에 테스트용 transport 가 꽂혀 있는지를 알려 줍니다. 운영에서는 False 입니다.
  6. share_ready 는 공유 링크 서명 비밀값(LC_SHARE_SECRET)이 32자 이상 설정됐는지를 알려 줍니다(share.py:81-83). 비어 있으면 공유가 꺼집니다.
  7. contracts.py 의 모듈 상수 TAXONOMY 를 그대로 돌려줍니다. 현재 프런트는 이 엔드포인트 대신 자체 data/relationship-types.json 을 쓰며, tests/test_frontend_taxonomy.py 가 그 파일이 이 사전과 일치하는지 검사합니다.

데코레이터가 실제로 하는 일을 설치 소스에서 확인합니다. app.get(...) 은 self.router.get(...) 으로, 다시 APIRouter.api_route(...) 로 위임되며, 그 안의 decorator 가 함수를 받아 라우터에 등록한 뒤 함수를 변형 없이 돌려줍니다.

프런트의 fetch 한 번은 어떤 층을 차례로 지나 JSON 으로 돌아옵니까?

출발점은 Next.js 프런트의 frontend/lib/api.ts 입니다. 이 함수 하나가 모든 엔드포인트 호출을 담당하며, 요청 헤더와 오류 처리 방식이 백엔드의 미들웨어·오류 모양과 짝을 이룹니다. 현재 백엔드를 호출하는 화면은 입력·결과 화면 frontend/app/test/page.tsx 와 공유 링크를 여는 frontend/app/r/page.tsx 두 곳이며, 정식 화면 frontend/app/page.tsx 는 정적 유형 사전만 씁니다.

  4. 라우터가 경로와 메서드로 핸들러를 고르고, 본문을 JSON 으로 파싱해 AnalysisInput 으로 검증합니다. 실패하면 RequestValidationError 가 나고 커스텀 핸들러가 422 를 만듭니다.

Starlette 의 미들웨어는 양파처럼 겹쳐지며, 요청은 바깥에서 안으로, 응답은 안에서 바깥으로 흐릅니다. 안쪽 미들웨어가 call_next 를 부르지 않고 응답을 바로 돌려주더라도, 바깥 미들웨어에게는 그 응답이 자기 call_next 의 반환값일 뿐이라 뒤처리가 똑같이 적용됩니다. 실제 앱에서 boundary 가 403 이나 415 로 끊은 응답에도 Cache-Control: no-store 가 붙어 있는 것이 그 증거이며, tests/test_api.py:36-40 이 이를 검사합니다.

원리 노트: pydantic-settings 의 소스 우선순위와 lru_cache

왜 모듈 전역 settings = Settings() 가 아니라 함수로 감쌌을까요. 함수로 감싼 실질적 효과는 두 가지입니다. boundary 와 response_headers: 라우터 앞뒤의 두 겹

요청이 핸들러에 닿기 전에 boundary 는 무엇을 검사하고, 응답은 나가기 전에 어떤 헤더를 얻습니까?

@app.middleware("http") 는 설치 소스를 보면 self.add_middleware(BaseHTTPMiddleware, dispatch=func) 한 줄의 단축 표기이고, Starlette 의 add_middleware 는 목록의 맨 앞에 끼워 넣습니다. 그래서 코드상 나중에 정의한 response_headers 가 바깥 겹, 먼저 정의한 boundary 가 안쪽 겹이 되어 요청은 response_headers → boundary → 라우터 순으로 흐릅니다. 실제 앱에서 app.user_middleware 를 찍어 보면 [response_headers, boundary] 순서로 나옵니다.

  1. salt 와 salt_time 은 바깥 함수의 지역 변수라서, 아래에서 재대입하려면 nonlocal 선언이 필요합니다.
  2. 상태를 바꾸는 POST 와 DELETE 만 Origin 을 봅니다. headers.get("origin") 은 헤더가 없으면 None 이고 None 은 허용 튜플에 들어 있으므로, Origin 이 없는 비브라우저 요청은 통과하고 허용 목록 밖 Origin 만 403 입니다.
  3. application/json; charset=utf-8 처럼 뒤에 붙는 매개변수를 떼고 앞부분만 비교합니다. JSON 이 아니면 핸들러에 닿기 전에 415 입니다.
  4. request.stream() 으로 본문을 청크 단위로 받으며 누적 크기를 셉니다. 40,960 바이트를 넘는 순간 나머지를 읽지 않고 413 을 돌려줍니다.
  5. 검사가 끝난 본문을 request._body 에 넣습니다. 미들웨어의 request 와 핸들러의 request 는 다른 객체이며, 이 속성이 있어야 Starlette 이 본문을 하류로 다시 흘려보냅니다. 이 줄이 없으면 핸들러는 빈 본문을 받아 422 를 냅니다.

AnalysisService 는 FastAPI 를 import 하지 않는 일반 클래스입니다. 생성자가 provider, 분류기, 해설기를 선택적으로 받아 테스트가 가짜를 끼울 수 있고, 단계별 동시 실행 제한 두 개를 인스턴스 안에 둡니다.

  4. 분류를 OpenAI 로 하는 모드에서는 해설 슬롯을 빌려 라벨을 받습니다. 어느 모드든 결과는 type_id 문자열 하나입니다.

단계 제한을 구현한 StageLimit 는 "FIFO 티켓 대기열"로 요약할 수 있습니다. 들어온 순서대로 티켓을 줄에 세우고, 자기 티켓이 맨 앞이면서 빈자리가 있을 때만 들어가며, 기한 안에 차례가 오지 않으면 AnalysisBusy 를 던집니다.

원리 노트: 스레드풀에서 threading 동기화가 통하는 이유

FastAPI 가 동기 핸들러를 anyio 의 WorkerThread(= threading.Thread)에서 실행하므로, 같은 프로세스의 threading.Lock, Condition, Semaphore 가 그대로 유효합니다. 반대로 Condition.wait() 로 기다리는 동안 워커 스레드 하나가 점유되며, anyio 4.15.1 의 기본 스레드 토큰은 40 개입니다. StageLimit 의 조건 변수와 술어 루프의 세부 원리, 그리고 왜 notify 가 아니라 notify_all 인지는 상 단계에서 봅니다.

왜 단계를 둘로 나눴을까요. concurrency.py 첫 줄의 "LLM 을 기다리는 동안 BERT 슬롯을 잡고 있지 말 것"이 이유입니다. BERT 추론은 CPU 를 쓰므로 2 개로 묶고, 해설은 네트워크 대기가 대부분이라 5 개까지 허용하며, 한 슬롯을 두 단계에 걸쳐 들고 있으면 느린 LLM 이 빠른 BERT 까지 막게 됩니다.

왜 threading.Semaphore 대신 직접 만든 티켓 줄일까요. 표준 threading.Semaphore 는 깨어나는 순서(FIFO)를 보장하지 않고 timeout 이 상대 시간이라, BERT·해설 두 단계가 하나의 절대 기한(deadline)을 나눠 쓸 수 없기 때문입니다. 직접 만든 deque 티켓 줄은 이 두 가지를 코드로 보장하며(concurrency.py:1 docstring "Per-instance FIFO stage limits"), tests/test_analysis_concurrency.py 의 test_fifo_timeout_and_exception_release 가 입장 순서 [1, 2] 와 예외 후 슬롯 반환을 검사합니다.

RequestValidationError 핸들러: 422 의 모양을 직접 정하기

검증 실패가 왜 FastAPI 기본 422 가 아니라 error() 모양으로 나가고, field 값은 어떻게 만들어집니까?

본문이 AnalysisInput 검증에 실패하면 FastAPI 는 RequestValidationError 를 던집니다. 이 예외를 누가 어떻게 응답으로 바꿀지는 app.exception_handler 로 등록한 함수가 정합니다.

@app.exception_handler(RequestValidationError) async def invalid(request, exc): loc = exc.errors()[0]["loc"] return error( "INVALID_REQUEST", 422, "입력값을 다시 확인해 주세요.", ".".join(str(x) for x in loc if x != "body"), )
  1. 예외 클래스를 키로 핸들러를 등록합니다. FastAPI 는 기본 핸들러를 setdefault 로 넣어 두므로 같은 키로 등록하면 프로젝트 것이 대체합니다.
  2. exc.errors() 는 오류 목록이지만 첫 번째의 loc 만 씁니다. 여러 필드가 틀려도 응답은 하나의 field 만 알려 줍니다.
  3. 미들웨어와 핸들러가 쓰는 같은 error() 헬퍼입니다. 메시지는 고정 문구라 입력값이 섞일 여지가 없습니다.
  4. loc 튜플에서 "body" 를 빼고 점으로 이으면 person_a.mbti 같은 경로가 됩니다. 리스트 인덱스가 섞여도 str() 로 문자열이 됩니다.

대체된 기본 핸들러를 보면 왜 바꿨는지가 보입니다. 기본 핸들러는 pydantic 의 오류 목록을 통째로 detail 에 실어 보내는데, pydantic 2 의 오류 항목에는 input 키로 틀린 입력값이 그대로 들어 있습니다.

async def request_validation_exception_handler( request: Request, exc: RequestValidationError ) -> JSONResponse: return JSONResponse( status_code=422, content={"detail": jsonable_encoder(exc.errors())}, )
  1. 시그니처는 프로젝트 핸들러와 같습니다. (request, exc) 를 받아 응답을 돌려주는 async 함수입니다.
  2. 상태 코드 422 는 같습니다. 러브코드가 바꾼 것은 본문의 모양입니다.
  3. exc.errors() 전체를 JSON 으로 만듭니다. 실험해 보면 {"type": "int_parsing", "loc": ["body", "n"], "msg": "...", "input": "notint"} 처럼 사용자가 보낸 값이 응답에 되돌아옵니다.

loc 의 첫 칸 "body" 는 pydantic 이 아니라 FastAPI 가 붙입니다. 본문 파라미터가 하나뿐이고 embed 가 아니면 loc=("body",) 를 접두로 삼아 pydantic 오류의 loc 앞에 이어 붙입니다.

if single_not_embedded_field: loc: tuple[str, ...] = ("body",) v_, errors_ = _validate_value_with_model_field( field=first_field, value=body_to_process, values=values, loc=loc ) return {first_field.name: v_}, errors_
  1. def analyse(body: AnalysisInput) 처럼 본문 파라미터가 하나면 이 분기입니다. 요청 JSON 전체가 그 모델 하나로 해석됩니다.
  2. 접두 ("body",) 입니다. 쿼리나 경로 파라미터였다면 "query", "path" 가 붙습니다.
  3. 모델 검증을 호출하고, 실패하면 _compat/v2.py:490 의 _regenerate_error_with_loc 가 loc_prefix + err["loc"] 로 경로를 완성합니다. 결과가 ("body", "person_a", "mbti") 입니다.

원리 노트: 예외 핸들러가 실행되는 위치

FastAPI 0.143.0 은 exception_handlers 사전에서 500 과 Exception 을 뺀 나머지를 ExceptionMiddleware 에 넘기고, 이 미들웨어는 사용자 미들웨어보다 안쪽에 놓입니다. 실제로 RequestValidationError 를 처음 잡는 try/except 는 라우트 레벨의 wrap_app_handling_exceptions 이며, ExceptionMiddleware 의 실질 역할은 핸들러 표를 scope["starlette.exception_handlers"] 에 올려 두는 것입니다. 어느 쪽이든 사용자 미들웨어 안쪽이므로 핸들러가 만든 422 응답도 response_headers 를 통과하며, 실제 앱의 422 응답에 cache-control: no-store 가 붙어 있는 것으로 확인됩니다.

왜 커스텀 핸들러를 두었을까요. 첫째, 응답 모양 통일입니다. 프런트의 api() 는 error.message 만 읽으므로 422 도 403 이나 503 과 같은 그릇에 담겨야 합니다.

둘째, 입력값 비노출입니다. tests/test_api.py:1-8 은 생년월일을 품은 카나리 문자열을 mbti 자리에 넣어 422 를 받은 뒤, 그 문자열이 응답 본문과 로그 어디에도 없음을 확인합니다.

셋째, 내부 구조 비노출입니다. pydantic 의 오류 타입 이름과 메시지 대신 필드 경로 하나만 내보내므로 서버가 어떤 라이브러리로 검증하는지 밖에서 알 수 없습니다. 기본 핸들러를 그대로 쓰는 흔한 구조와 비교하면 디버깅 정보는 줄지만, 개인정보를 다루는 입력에서는 이 쪽이 맞는 선택입니다.
